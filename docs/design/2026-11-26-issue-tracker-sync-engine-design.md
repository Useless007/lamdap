# เอกสารออกแบบ: Lamdap — issue tracker แบบ local-first พร้อม sync engine ที่เขียนเอง บน RR stack

- วันที่: 26 พ.ย. 2569 (2026-11-26)
- สถานะ: รอเจ้าของอนุมัติ (ฉบับที่ 4: สร้างบน RR stack และแก้ตามการทบทวนครั้งที่ 2)
- ผู้ทำ: Useless007 (เจ้าของ ดูแล server และ sync engine) และ jxyluvcode (ดูแลหน้าจอ และร่วมใช้งาน)

ป้ายที่ใช้ทั้งเอกสาร:

- **[เจ้าของ]** สิ่งที่เจ้าของพูดหรือเลือกเอง
- **[ข้อเสนอ]** ค่าเริ่มต้นที่เสนอในการออกแบบ เจ้าของค้านได้
- **[ผู้สร้าง]** สิ่งที่ปล่อยให้คนลงมือสร้างตัดสิน

## 1. สรุปสำหรับอนุมัติ

### 1.1 จะได้อะไร

- เว็บแอปติดตามงานสำหรับทีมเล็ก ใช้คีย์บอร์ดเป็นหลัก แก้แล้วเห็นผลทันที เห็นการแก้ของอีกคนสด และใช้ต่อได้ตอนไม่มีเน็ต
- Sync engine ที่เขียนเอง: ฝั่ง server เป็น Rust บน Postgres ฝั่งเครื่องเป็น TypeScript พร้อมชุดทดสอบจำลองที่เป็นหลักฐานว่าข้อมูลไม่เพี้ยนและไม่หาย
- แอปจริงตัวแรกที่สร้างบน [RR stack](https://github.com/Useless007/rr-stack) ของเจ้าของ เพื่อแสดงว่า stack นี้รับงานที่เกินกว่า CRUD ได้
- Repo สาธารณะ, เดโมที่คนนอกลองได้โดยไม่ต้องสมัคร และบทความอธิบายว่า engine ทำงานอย่างไร
- แบ่งเป็น 5 ช่วง: M0 วางฐาน, M1 engine กับ server ครบและใช้งานจริงได้, M2 หน้าจอครบ, M3 ทำงานตอน offline, M4 พร้อมใส่ portfolio (รายละเอียดข้อ 15)

### 1.3 ค่าเริ่มต้นที่เสนอ (ค้านได้)

- **รูปแบบการ sync** เครื่องส่งการแก้ไขและดึงความเปลี่ยนแปลงผ่าน HTTP ซึ่งอยู่ในสัญญา `openapi.json` ส่วน WebSocket ใช้แค่สะกิดว่ามีของใหม่ และปิดได้โดยระบบยังถูกต้อง
- **การ host** ต้องให้เจ้าของตัดสินหลังการทดลองใน M0 เพราะแผนฟรีของ Vercel กับ Neon ไม่พอสำหรับ WebSocket ที่เปิดค้าง (ตัวเลขอยู่ในข้อ 4) ทางเลือกคือเครื่องของตัวเองที่มีการสะกิด หรือ Vercel กับ Neon แผนฟรีแบบไม่มีการสะกิด ซึ่งการแก้ของอีกคนจะมาช้ากว่า
- **ระบบปิด** ใช้ระบบ login ด้วยอีเมลกับรหัสผ่านของแม่แบบ แต่สมัครได้เฉพาะผู้ที่มีรหัสเชิญ
- **เดโม** เป็นระบบแยกอีกชุดที่มีฐานข้อมูลของตัวเอง เข้าได้โดยไม่ต้องสมัคร และถูกล้างทุกวัน
- **Offline** รวมถึงการเปิดแอปขณะไม่มีเน็ต
- **หลายแท็บ** ตั้งแต่ M3 มีแท็บเดียวต่อเบราว์เซอร์ที่ทำงาน sync คือแท็บที่กำลังใช้อยู่ แท็บอื่นหยุดชั่วคราว
- **รายละเอียดของ issue** บันทึกเมื่อกดบันทึกหรือออกจากช่อง server ไม่รับการบันทึกที่จะทับข้อความซึ่งผู้บันทึกยังไม่เคยเห็น
- **ข้อมูลใน workspace จริงถือว่าถาวรตั้งแต่ M1** ป้องกันด้วยการสำรองระดับฐานข้อมูล ส่วนการกู้คืนทีละ workspace จากไฟล์ส่งออกไม่อยู่ในรุ่นแรก
- **การลบ** คือย้ายลงถังขยะและกู้คืนได้ รุ่นแรกไม่มีการลบถาวร
- **ลืมรหัสผ่าน** เจ้าของระบบออกรหัสตั้งรหัสผ่านใหม่ให้ เพราะรุ่นแรกไม่ส่งอีเมล
- สถานะงานมี 5 ค่าตายตัว ความสำคัญมี 5 ค่าตายตัว
- รุ่นแรกยังไม่มี comment, undo และการแจ้งเตือน
- ออกแบบให้ลื่นที่ 10,000 issue และ 20 สมาชิกต่อ workspace
- ตัวหนังสือบนปุ่มและเมนูเป็นภาษาอังกฤษ เนื้อหาพิมพ์ไทยได้เต็มรูปแบบ วันที่แสดงตามภาษาของเบราว์เซอร์
- README เป็นภาษาอังกฤษ ภาษาของบทความตัดสินตอนเริ่ม M4
- ไม่มีกำหนดส่ง ทำตามลำดับ M0 ถึง M4

## 2. ที่มาและเหตุผล

- **[เจ้าของ]** อยากได้เครื่องมือติดตามงานที่ปรับแต่งเป็นของตัวเอง และอยากมีผลงานติดตัวไว้ใส่ portfolio
- ตั้งต้นจาก repo `linear/linear` แต่ตรวจแล้วพบว่าเป็น SDK ไม่ใช่ตัวแอป จึงไม่มีอะไรให้ fork
- **[เจ้าของ]** เลือกสร้าง issue tracker ของตัวเองแนวเดียวกับ Linear และให้เพื่อน (jxyluvcode) เข้ามาทั้งเขียนโค้ดและใช้งานด้วยกัน
- **[เจ้าของ]** เลือกเขียน sync engine เอง เพื่อให้เป็นผลงานที่แสดงฝีมือทางวิศวกรรมได้เต็มที่
- **[เจ้าของ]** เลือกสร้างบน RR stack ซึ่งเป็น starter ของเจ้าของเอง เพื่อให้ Lamdap เป็นตัวอย่างจริงที่ชู stack นี้
- **[เจ้าของ]** เลือก license ที่สงวนสิทธิ์เชิงพาณิชย์ เพราะถ้างานออกมาดี ต้องการรักษาสิทธิ์นั้นไว้

สิ่งที่เจ้าของยังไม่ได้บอก และเอกสารนี้ตั้งสมมติฐานแทน:

- ตอนนี้ใช้เครื่องมืออะไรติดตามงาน และขัดใจตรงไหน: ไม่ทราบ จึงยึดขอบเขตรุ่นแรกที่เสนอไปและเจ้าของไม่ได้ค้าน
- Portfolio จะให้ใครดู: สมมติว่าเป็นคนสายเทคนิค จึงเน้นหลักฐานทางวิศวกรรมและเดโมที่ลองได้ทันที
- กำหนดเวลาและเวลาที่แต่ละคนมีต่อสัปดาห์: ไม่ทราบ จึงถือว่าไม่มีกำหนดส่ง
- งบค่า host ต่อเดือน: ไม่ทราบ จึงเสนอทั้งทางที่ฟรีและทางที่มีค่าใช้จ่าย ให้เจ้าของเลือกใน M0

## 3. เป้าหมาย สิ่งที่ไม่ทำ และสิ่งที่ถือว่าล้มเหลว

### เป้าหมาย

- **G1** เจ้าของกับเพื่อนใช้ติดตามงานจริงทุกวัน
- **G2** อ้างใน portfolio ได้ว่า "เขียน sync engine เอง และพิสูจน์ได้ว่าถูกต้อง" มี repo, เดโม และบทความรองรับ
- **G3** สองคนทำงานขนานกันได้โดยไม่ชนกัน
- **G4** Lamdap เป็นตัวอย่างจริงของ RR stack: ทำตามแนวทางของ stack และสิ่งที่ต้องเพิ่มเกินแม่แบบถูกบันทึกไว้ให้นำกลับไปปรับปรุง stack ได้

### ไม่ทำในรุ่นแรก

- Comment, undo/redo, การแจ้งเตือน, ประวัติการแก้ไขที่ดูได้ในหน้าจอ
- Cycle, roadmap, สถานะงานที่ตั้งเอง, ทีมย่อยหรือสิทธิ์ที่ละเอียดกว่า owner กับ member
- การพิมพ์พร้อมกันในข้อความเดียวกัน, การแสดงว่าใครกำลังดูอะไรอยู่
- หลายแท็บที่ทำงานสดพร้อมกันหลัง M3 (ดูข้อ 8.8)
- แอปมือถือ, การเชื่อมกับบริการอื่น, ไฟล์แนบและรูปภาพ, การส่งอีเมล
- ช่องทางให้ AI agent เปิดและอัปเดต issue (เก็บไว้เป็นรุ่นสอง)
- การโหลดข้อมูลบางส่วนสำหรับ workspace ที่ใหญ่กว่าเพดานในข้อ 4
- การนำเข้าข้อมูลจากเครื่องมืออื่น, การกู้คืนทีละ workspace จากไฟล์ส่งออก, การลบถาวรโดยผู้ใช้, หลายภาษาใน UI
- การแก้ไขหลายรายการแบบสำเร็จพร้อมกันทั้งหมดเมื่อเกิน 50 รายการ
- การ render หน้าของแอปที่ server (ใช้โหมด prerender กับ SPA ของแม่แบบ)
- การรันแกน server ในเบราว์เซอร์

### ถือว่าล้มเหลว แม้ใช้งานได้

- **A1** หน้าตาหรือชื่อเหมือน Linear จนดูเป็นของลอก
- **A2** ข้อมูลที่ผู้ใช้พิมพ์หายไปเงียบ ๆ
- **A3** Engine ทำงานได้ในเดโม แต่ไม่มีหลักฐานว่าถูกต้อง และผู้ทำอธิบายไม่ได้ว่ามันทำงานอย่างไร
- **A4** เดโมสาธารณะทำให้ workspace จริงใช้งานไม่ได้ หรือเข้าถึงข้อมูลจริงได้
- **A5** สองคนแก้ไฟล์ชนกันเป็นประจำ
- **A6** โค้ดฝืนแนวทางของ RR stack จนใช้เป็นตัวอย่างของ stack ไม่ได้

## 4. ข้อจำกัด

### แนวทางของ RR stack ที่ต้องทำตาม

- งานถือว่าเสร็จเมื่อ `bun run check` จบด้วย exit code 0 เท่านั้น ถ้าแก้อะไรใต้ `web/app` ต้องรัน `bun run e2e` ด้วย และถ้าแก้วิธีที่ server เสิร์ฟหน้าหรือไฟล์ ต้องรัน `bun run smoke` ด้วย
- ห้ามแก้ด้วยมือ: `openapi.json`, `web/app/api/**`, `server/.sqlx/**` ทั้งหมดสร้างจากคำสั่งของ stack
- type ที่ข้ามสายมีต้นทางเดียว คือ struct ของ Rust ที่ derive `ToSchema` ฝั่ง TypeScript ใช้ type จาก `~/api` เท่านั้น ห้ามเขียน type ที่ข้ามสายเอง
- ตรวจข้อมูลที่ขอบด้วย newtype, ไม่มี `unwrap` หรือ `expect` นอกเทสต์, ใช้ `AppJson`, `AppPath`, `AppQuery` และ `CurrentUser` ของแม่แบบ, ตรวจสิทธิ์ใน SQL
- Rust เขียนแบบตรงไปตรงมา ไม่มี macro ของตัวเอง ไม่มีชั้น abstraction ทั่วไป
- migration เป็นไฟล์ใหม่ที่มีเลขกำกับเสมอ ห้ามแก้ไฟล์ที่ commit แล้ว
- script เป็น TypeScript ที่รันด้วย bun ใช้ได้ทั้ง Linux และ Windows

### การ host และค่าใช้จ่าย

ข้อเท็จจริงของ Vercel แผน Hobby กับ Neon แผนฟรี ซึ่งเป็นทางที่ RR stack รองรับและเดโมของ stack ใช้อยู่ แหล่งอยู่ในข้อ 18:

| เรื่อง | ข้อเท็จจริง |
|---|---|
| หน่วยความจำของ Vercel | แต่ละ instance ใช้ 2 GB ตายตัว แผน Hobby ให้ 360 GB-ชั่วโมงต่อเดือน เท่ากับ 180 ชั่วโมงของ instance |
| การคิดเวลา | การเชื่อมต่อที่เปิดค้าง รวมถึง WebSocket ทำให้ instance ถูกคิดเวลาจนกว่าจะปิด |
| เมื่อเกินโควตาของ Vercel | deployment ทั้งหมดของทีมถูกหยุด และไม่กลับมาเอง |
| WebSocket | ถูกตัดทุก 300 วินาที |
| การหลับ | container ที่ไม่มีคนใช้ราว 5 นาทีจะหลับ และ request แรกหลังจากนั้นช้ากว่าปกติ |
| ขนาด | request และ response ไม่เกิน 4.5 MB |
| ที่ตั้ง | แผน Hobby รันในภูมิภาคเดียว ค่าตั้งต้นคือฝั่งตะวันออกของสหรัฐ |
| สถานะ | Container Runtime ยังเป็นรุ่น beta |
| Neon | แผนฟรีให้เวลาประมวลผลจำกัดต่อโปรเจกต์ต่อเดือน (ราว 400 ชั่วโมงที่ขนาดเล็กสุด) เมื่อหมดแล้วฐานข้อมูลถูกพักจนถึงรอบถัดไป และตัว pooler ใช้กับ LISTEN ไม่ได้ |

ผลของตัวเลขเหล่านี้:

- แท็บเดียวที่เปิด WebSocket ค้างทั้งเดือนใช้ราว 1,460 GB-ชั่วโมง เกินโควตา 4 เท่า สองคนที่ใช้วันละ 9 ชั่วโมง 22 วัน บน instance แยกกัน ใช้ราว 396 GB-ชั่วโมง ซึ่งก็เกิน
- ถ้าเกิน ทุกโปรเจกต์ในทีม Vercel เดียวกันหยุดไปด้วย รวมถึงโปรเจกต์อื่นของเจ้าของ
- ดังนั้น **WebSocket ที่เปิดค้างใช้กับ Vercel แผนฟรีไม่ได้** ส่วนการดึงข้อมูลเป็นครั้งสั้น ๆ ใช้ได้ เพราะถูกคิดเวลาเฉพาะช่วงที่ประมวลผล

ทางเลือกสำหรับระบบจริง **[เจ้าของตัดสินหลังการทดลองใน M0]**:

| | เครื่องของตัวเอง หรือ VPS | Vercel + Neon แผนฟรี |
|---|---|---|
| วิธี deploy | `compose.prod.yml` กับ Caddy ของแม่แบบ | ตามเอกสาร deploy ของแม่แบบ |
| การสะกิด | เปิด WebSocket ค้างได้ การแก้ของอีกคนมาภายใน 1 วินาที | ปิดการสะกิด เครื่องดึงเองเป็นรอบ การแก้ของอีกคนมาช้าเท่ารอบการดึง |
| ค่าใช้จ่าย | ศูนย์ถ้าใช้เครื่องที่มีอยู่ หรือค่าเช่า VPS รายเดือน | ศูนย์ |
| ความเสี่ยง | ต้องดูแลเครื่องและการสำรองเอง | หลับเมื่อไม่มีคนใช้, เพดานเวลาของ Neon, รุ่น beta |

การออกแบบรองรับทั้งสองทางด้วยโค้ดชุดเดียว เพราะการสะกิดมีผลต่อความเร็วเท่านั้น ไม่มีผลต่อความถูกต้อง (ข้อ 6 หลักที่ 6)

ข้อกำหนดที่ใช้กับทุกที่ host:

- server กับฐานข้อมูลต้องอยู่ภูมิภาคเดียวกัน เพราะล็อกของ workspace ถูกถือข้ามคำสั่งฐานข้อมูลหลายคำสั่ง
- เดโมกับระบบจริงต้องไม่อยู่ในทีม Vercel เดียวกัน และไม่ใช้ฐานข้อมูลร่วมกัน
- เครื่องมือที่ต้องมีในเครื่องของผู้พัฒนา: Docker, Rust stable, bun 1.4 ขึ้นไป, git และ sqlx-cli

### ขนาดที่ออกแบบรองรับ **[ข้อเสนอ]**

- ไม่เกิน 10,000 issue และ 20 สมาชิกต่อ workspace
- การกระทำในเครื่อง (เปิด issue, เปลี่ยนสถานะ, กรอง) แสดงผลภายใน 100 ms ที่ 10,000 issue
- การแก้ของอีกคนปรากฏภายใน 1 วินาที เมื่อเปิดการสะกิด ทั้งสองเครื่องเชื่อมต่ออยู่ และ server ไม่ได้หลับ เมื่อปิดการสะกิด ปรากฏภายในหนึ่งรอบการดึง

### อื่น ๆ

- รองรับ Chrome, Edge, Firefox, Safari รุ่นปัจจุบันบน desktop หน้าจอมือถือเปิดได้แต่ไม่ได้ปรับให้เหมาะ
- Repo คือ `Useless007/lamdap` เป็น public มี `jxyluvcode` เป็น collaborator แต่ละคน commit ด้วยตัวตน git ของตัวเอง
- เพราะ repo เป็น public ทุกอย่างที่ commit ต้องเปิดเผยได้: ไม่มี secret ไม่มีข้อมูลของงานอื่น และไม่มีข้อมูลส่วนตัว

- สิ่งที่เจ้าของต้องทำเอง เพราะเป็นการสร้าง secret หรือ login แบบโต้ตอบ: บัญชีและการ login ของที่ host, ค่า secret ของ production

## 6. ภาพรวมสถาปัตยกรรม

```
แท็บเบราว์เซอร์ (React Router แบบ SPA)
 ├─ UI: หน้าจอ + ทะเบียนคำสั่งคีย์บอร์ด
 └─ Sync client (TypeScript)
      ├─ base     สำเนาที่ server ยืนยันแล้ว ณ ตำแหน่งหนึ่ง
      ├─ pending  คิวคำสั่งแก้ไขของเครื่องนี้ที่ยังไม่รู้ผลหรือยังไม่ถึง base
      ├─ view     base ทับด้วย pending  ← UI อ่านจากตรงนี้เท่านั้น
      └─ ที่เก็บในเครื่อง (หน่วยความจำ → IndexedDB ใน M3)
          │
          │  push   POST  ส่ง mutation              ┐
          │  pull   GET   ดึง delta หลังตำแหน่งของเครื่อง ├ อยู่ใน openapi.json
          │  boot   GET   โหลดครั้งแรกทีละหน้า        ┘
          │  poke   WebSocket  server สะกิดว่ามีของใหม่ (ปิดได้)
          ▼
Axum (binary เดียว: API + หน้าเว็บที่ build แล้ว)  อาจมีหลายตัวพร้อมกัน
          │
          ▼
Postgres: ผู้ใช้, session, workspace, สมาชิก, ตารางข้อมูลงาน,
          บันทึกความเปลี่ยนแปลงเรียงตาม syncId, ตาราง client, ผลการปฏิเสธ
```

หลักที่ทั้งระบบยึด:

1. **Server เป็นตัวจริงเสมอ** สำเนาในเครื่องล้างแล้วโหลดใหม่ได้ทุกเมื่อ
2. **Server เป็นผู้จัดลำดับ** ทุกการแก้ไขที่ถูกรับจะได้เลข `syncId` ที่เพิ่มขึ้นทีละหนึ่งภายใน workspace
3. **UI ไม่รอ server** UI อ่านจาก view และเขียนผ่านคำสั่งแก้ไขเท่านั้น
4. **ส่งซ้ำได้โดยไม่เกิดผลซ้ำ** mutation เดียวกันส่งกี่ครั้งก็มีผลครั้งเดียว
5. **ไม่มีการแก้ไขใดหายเงียบ** ทุกคำสั่งจบด้วยการถูกรับ หรือถูกปฏิเสธพร้อมแจ้งผู้ใช้และเก็บเนื้อหาไว้ให้
6. **ความถูกต้องอยู่ที่ Postgres ไม่ใช่ที่การสะกิด** การสะกิดหายได้ ซ้ำได้ มาช้าได้ หรือปิดไปเลยก็ได้ โดยข้อมูลไม่ผิด เพราะข้อมูลทุกชิ้นเดินทางผ่าน pull
7. **ทุกการเปลี่ยนแปลงของข้อมูลที่ sync ผ่านบันทึกทางเดียว** ไม่มีโค้ดใดแก้ตารางเหล่านี้โดยไม่ลงบันทึก รวมถึง migration ที่แก้ข้อมูลและการใส่ข้อมูลตัวอย่าง
8. **เครื่องตรวจได้ว่าประวัติของตนยังตรงกับ server** ถ้าไม่ตรง เช่น หลังการกู้คืนฐานข้อมูล เครื่องโหลดใหม่เองโดยไม่ต้องมีใครสั่ง

## 7. ข้อมูล

ทุก workspace มีข้อมูลชุดนี้ และสมาชิกทุกคนเห็นทั้งหมด

| Model | ฟิลด์หลัก |
|---|---|
| Workspace | id, ชื่อ, key สำหรับเลข issue (เช่น `LMD`) |
| Member | userId, ชื่อที่แสดง, บทบาท (owner หรือ member), removed |
| Project | id, ชื่อ, คำอธิบาย, สี, sortKey, deletedAt |
| Label | id, ชื่อ, สี, deletedAt |
| Issue | id, number, หัวข้อ, สถานะ, ความสำคัญ, assigneeId, projectId, sortKey, createdBy, createdAt, updatedAt, deletedAt |
| IssueDescription | issueId, ข้อความ (markdown), rev |
| IssueLabel | issueId, labelId, removed |

กติกาของข้อมูล **[ข้อเสนอ]**:

- **id** ของ project, label และ issue เครื่องสร้างเองเป็น UUID v7 จึงสร้างข้อมูลตอน offline ได้ ส่วน id ของผู้ใช้เป็นเลขที่ server ออกตามแม่แบบ
- **number** ของ issue server เป็นผู้ออกตอนรับคำสั่ง issue ที่สร้างตอน offline แสดงเลขชั่วคราวจนกว่าจะ sync และต้องเปิดกับลิงก์ได้ด้วย id ตั้งแต่ก่อนมีเลข
- **ค่าที่ server เป็นผู้กำหนด** คือ number, createdBy, createdAt, updatedAt, deletedAt และ rev ไม่เชื่อนาฬิกาหรือค่าเหล่านี้จากเครื่อง
- **รายละเอียดแยกเป็นแถวของตัวเอง** เพราะเป็นฟิลด์เดียวที่ใหญ่ การแยกทำให้แถวของ issue เล็กเสมอ แถวนี้ถูกสร้างพร้อม issue ทุกครั้ง แม้ข้อความว่าง
- **rev** ของรายละเอียดคือ `syncId` ของการเปลี่ยนแปลงครั้งล่าสุดของแถวนั้น เริ่มที่ `syncId` ของการสร้าง issue
- **สถานะ** มี 5 ค่า: backlog, todo, in_progress, done, canceled
- **ความสำคัญ** มี 5 ค่า: none, urgent, high, medium, low
- **ลำดับในคอลัมน์** ใช้ sortKey แบบ fractional index เป็นข้อความ ถ้าสองรายการมี sortKey เท่ากัน ให้แสดงเรียงตาม id และเครื่องต้องออก sortKey ใหม่ให้รายการที่เท่ากันก่อนแทรกระหว่างกลาง
- **Label ของ issue** เก็บเป็นแถวเชื่อม ไม่เก็บเป็น array ใน issue เพราะสองคนติด label คนละอันพร้อมกันต้องไม่ทับกันหาย
- **การลบ** ของ issue, project, label คือการย้ายลงถังขยะ ผู้ใช้กู้คืนได้ รุ่นแรกผู้ใช้สั่งได้แค่สร้างกับแก้ไข จึงไม่มีกรณีแก้ไขชนกับการลบถาวร
- **ขนาด** หัวข้อไม่เกิน 500 ตัวอักษร รายละเอียดไม่เกิน 100 KB
- ทุกตารางของข้อมูลงานมี workspace อยู่ใน primary key id ที่ซ้ำกันข้าม workspace จึงไม่กระทบกันและไม่เผยว่ามีอยู่

## 8. Sync engine

### 8.1 คำศัพท์

- **Client** ตัวตนของผู้ส่งคำสั่ง มี `clientId` เป็นค่าสุ่ม ผูกกับผู้ใช้คนเดียวและ workspace เดียวตลอดไป (ข้อ 8.6 บอกว่าสร้างเมื่อไร)
- **Mutation** คำสั่งแก้ไขหนึ่งชุด มีสามอย่างกำกับ
  - `mutationId` คือตำแหน่งในคิวของ client นับ 1, 2, 3
  - `uid` คือรหัสสุ่มประจำ mutation ที่ไม่เปลี่ยนตลอดชีวิตของมัน
  - เวอร์ชันของ protocol ที่ใช้ตอนสร้าง

  เนื้อหาเป็นรายการ op แบบสร้างหรือแก้ไข หรือเป็น **mutation ว่าง** ที่ไม่มี op และมีไว้เพื่อใช้เลขให้หมดไป server รับทั้งชุดหรือไม่รับเลย
- **Delta** ผลของ mutation หนึ่งชุดที่ถูกรับ มี `syncId`, **ป้าย** ซึ่งเป็นค่าสุ่มประจำ delta, รายการแถวที่เปลี่ยนในสภาพหลังเปลี่ยนทั้งแถว และ **ที่มา** คือ `clientId`, `mutationId` กับ `uid` (ว่างถ้า server เป็นผู้เริ่มเอง) เครื่องนำ delta ไปใช้ด้วยการแทนที่แถว การใช้ซ้ำตามลำดับจึงให้ผลเท่าเดิม
- **ตำแหน่ง** ของเครื่องคือ `lastSyncId` คู่กับป้ายของ delta ที่เลขนั้น server ใช้คู่นี้ตรวจว่า base ของเครื่องเป็นส่วนต้นของประวัติบน server จริง
- **ผลของ mutation** มีสามแบบ
  - **รับแล้ว ที่ syncId S** ถูกบันทึกถาวร
  - **ปฏิเสธ พร้อมเหตุผล** ถูกบันทึกถาวร
  - **ยังไม่ได้บันทึก** ไม่มีอะไรถูกบันทึก mutation ยังค้างอยู่และจะส่งใหม่ภายหลัง
- **Push, pull, poke** สามช่องทางระหว่างเครื่องกับ server: ส่ง mutation, ดึง delta และการสะกิดว่ามี delta ใหม่

### 8.2 ฝั่ง server: push

request หนึ่งครั้งมี `clientId`, ตำแหน่งของเครื่อง และรายการ mutation เรียงตามเลข

**ก่อนประมวลผล** server ตรวจตำแหน่งของเครื่อง ถ้าบันทึกไม่มีแถวที่ `lastSyncId` นั้น หรือป้ายไม่ตรง ให้ตอบว่า "ประวัติไม่ตรง" และไม่ประมวลผล mutation ใดเลย

**จากนั้นประมวลผลทีละ mutation ตามลำดับ** แต่ละ mutation อยู่ใน transaction ของตัวเอง:

1. **ตอบซ้ำโดยไม่ล็อก** ถ้า `mutationId` ไม่เกินเลขล่าสุดที่ประมวลผลแล้วของ client ให้อ่านผลที่บันทึกไว้ ถ้า `uid` ตรงกัน ตอบผลเดิม ถ้า `uid` ไม่ตรง ตอบผลแบบ "เลขซ้ำ" ซึ่งเครื่องต้องแสดงให้ผู้ใช้เห็น ผลที่บันทึกแล้วไม่มีวันเปลี่ยน จึงไม่ต้องล็อก
2. **ล็อก workspace** ด้วยการล็อกแถวของ workspace จนจบ transaction โดยรอได้ไม่เกินเวลาที่กำหนด ทุกการเขียนของ workspace เดียวกันจึงเรียงทีละรายการ และลำดับการ commit ตรงกับลำดับของ `syncId` เสมอ ไม่ว่ามี server กี่ตัว
3. **ตรวจสมาชิกภาพและเจ้าของ client** ภายใน transaction เดียวกัน การถอดสมาชิกก็ต้องถือล็อกเดียวกัน จึงไม่มีช่องให้คนที่เพิ่งถูกถอดเขียนได้
4. **เลื่อนเลขของ client แบบมีเงื่อนไข** จาก `mutationId` ลบหนึ่ง เป็น `mutationId` ถ้าเลื่อนไม่ได้ แปลว่ามี request อื่นประมวลผลไปแล้ว ให้ตอบผลที่บันทึกไว้ หรือแปลว่ามีช่องว่าง ให้ตอบว่ารอเลขไหนอยู่และหยุดประมวลผลรายการที่เหลือ ขั้นนี้ทำให้ mutation หนึ่งมีผลได้แบบเดียว แม้มีสอง request ของ client เดียวกันวิ่งพร้อมกัน
5. **ตรวจข้อมูล** ตามกติกาในข้อ 8.4 เนื้อหาที่อ่านไม่ออกหรือผิดรูปแบบถือเป็นการปฏิเสธของ mutation นั้น ไม่ใช่ความผิดพลาดของทั้ง request เพื่อไม่ให้ mutation เดียวขวางคิวตลอดไป
6. **บันทึก** ลงตารางข้อมูล พร้อมค่าที่ server เป็นผู้กำหนด
7. **ลงบันทึก** ผ่านทางเดียวของระบบ: `syncId` ใหม่คือเลขล่าสุดในแถวของ workspace ที่ล็อกอยู่บวกหนึ่ง ไม่ใช้ sequence ของฐานข้อมูล บันทึก delta พร้อมป้ายและที่มา แล้วสั่ง NOTIFY ภายใน transaction เดียวกัน การสะกิดจึงออกไปก็ต่อเมื่อ commit สำเร็จ

กรณีที่ไม่ได้จบด้วยการรับ:

- **ปฏิเสธในขั้น 5 หรือเป็น mutation ว่าง** ไม่แก้ข้อมูล แต่การเลื่อนเลขในขั้น 4 ยังอยู่ และบันทึกผลการปฏิเสธพร้อมเหตุผลกับ `uid`
- **โค้ดของ server ผิดพลาดระหว่างประมวลผล รวมถึง panic** ต้องถูกจับเป็นราย mutation ยกเลิก transaction นั้น แล้วบันทึกเป็นการปฏิเสธด้วยเหตุผล `server-error` โดยทำขั้น 2 ถึง 4 ใหม่ใน transaction ใหม่ ถ้าขั้น 4 พบว่ามี request อื่นประมวลผลไปแล้ว ให้ตอบผลนั้นแทน
- **ความล้มเหลวชั่วคราว** คือ การเชื่อมต่อฐานข้อมูลหลุด, หมดเวลารอล็อกหรือรอการเชื่อมต่อ, deadlock หรือการชนกันของ transaction, ทรัพยากรไม่พอ และคำสั่งถูกยกเลิกเพราะหมดเวลา ไม่มีอะไรถูกบันทึก ผลคือ "ยังไม่ได้บันทึก" และหยุดประมวลผลรายการที่เหลือ ข้อผิดพลาดอื่นของฐานข้อมูลถือเป็นความผิดพลาดของโค้ด
- **หมดเวลาของ request** แต่ละ request มีงบเวลา mutation ที่ยังไม่ถึงคิวได้ผล "ยังไม่ได้บันทึก"

คำตอบของ push มีผลของแต่ละ mutation และ `syncId` ล่าสุดของ workspace เครื่องจึง pull ต่อได้ทันทีโดยไม่ต้องรอการสะกิด

เงื่อนไขที่ทำให้ลำดับถูกต้อง: `syncId` มาจากแถวที่ล็อกอยู่เท่านั้น และ transaction ใช้ระดับการแยกตั้งต้นของ Postgres ห้ามยกระดับ

การเปลี่ยนแปลงที่ server เป็นผู้เริ่มเอง เช่น มีสมาชิกเข้าใหม่ หรือการใส่ข้อมูลตัวอย่าง ใช้ล็อกและทางลงบันทึกเดียวกัน migration ที่ต้องแก้ข้อมูลในตารางที่ sync ก็ต้องลงบันทึกเช่นกัน

### 8.3 ฝั่ง client

mutation หนึ่งชุดผ่านสถานะตามลำดับ: สร้างในเครื่อง, เข้าคิว (ได้ `mutationId` กับ `uid` แล้ว), ส่งแล้ว, รู้ผลแล้ว

**กติกาหลัก: เลขทุกเลขที่ออกแล้วต้องไปถึง server** เครื่องห้ามทิ้ง mutation ที่ได้เลขแล้วออกจากคิวเอง เพราะ server จะรอเลขนั้นตลอดไปและคิวที่ตามมาจะค้าง ถ้า mutation ใดส่งตามเดิมไม่ได้แล้ว ให้ส่งเป็น mutation ว่างด้วยเลขและ `uid` เดิม แล้วย้ายเนื้อหาเดิมไปยังรายการที่ไม่สำเร็จ

- **เมื่อผู้ใช้แก้ไข** ต่อท้าย pending และคำนวณ view ใหม่ทันที จากนั้นออกเลขและ push ตามลำดับเมื่อเชื่อมต่อได้
- **เมื่อไร pull** หลัง push สำเร็จ, เมื่อถูกสะกิด, เมื่อเชื่อมต่อใหม่หรือกลับมาที่แท็บ และตามรอบเวลาขณะแท็บแสดงอยู่
- **เมื่อได้รับ delta** ต้องเป็น `syncId` ถัดจาก `lastSyncId` พอดี จึงนำไปใช้กับ base และจำป้ายของมันเป็นตำแหน่งใหม่ ถ้าเลขซ้ำให้ข้าม ถ้าเลขข้ามให้ pull ใหม่จากตำแหน่งเดิม
- **mutation ออกจาก pending ได้สามกรณีเท่านั้น**
  1. ถูกปฏิเสธ
  2. เครื่องนำ delta ที่มีที่มาเป็น mutation นั้นไปใช้
  3. คำตอบของ push บอกว่ารับแล้วที่ S และ S ไม่เกิน `lastSyncId` ของเครื่อง ซึ่งเชื่อได้เพราะ request เดียวกันนั้นผ่านการตรวจตำแหน่งมาแล้ว
- **เมื่อรู้ว่ารับแล้วที่ S ที่เกิน `lastSyncId`** ให้จำไว้เพื่อไม่ส่งซ้ำ และรอกรณีที่ 2 ถ้า `lastSyncId` ผ่าน S ไปแล้วโดยไม่เจอ delta ของตัวเอง แปลว่าประวัติเปลี่ยน ให้ลืมสิ่งที่จำไว้แล้วส่งใหม่
- **เมื่อถูกปฏิเสธ** ย้ายไปยังรายการที่ไม่สำเร็จพร้อมเนื้อหาและเหตุผล view กลับไปเป็นค่าของ base ผู้ใช้เลือกส่งใหม่หรือทิ้ง ถ้าการสร้างถูกปฏิเสธ mutation ที่ค้างอยู่ซึ่งแตะแถวเดียวกันยังอยู่ในคิวและถูกส่งตามปกติ server จะปฏิเสธตาม แล้วรายการที่ไม่สำเร็จจึงรวมทั้งหมดเป็นร่างเดียว
- **เมื่อผลคือยังไม่ได้บันทึก หรือ request ไม่สำเร็จ** mutation ยังอยู่ใน pending ส่งใหม่ด้วยเลขและ `uid` เดิมโดยหน่วงเวลาเพิ่มขึ้นพร้อมสุ่ม และบอกผู้ใช้ว่า server บันทึกไม่ได้ชั่วคราว
- **เมื่อ server ตอบว่ารอเลขอื่นอยู่** โหลดคิวจากที่เก็บในเครื่องใหม่ แล้วส่งตั้งแต่เลขที่ server รอ ถ้าเครื่องไม่มีเลขนั้น เป็นบั๊ก เครื่องหยุดส่ง แสดงสถานะผิดพลาด และเก็บคิวไว้ครบ
- **เมื่อ request ถูกตอบว่าผิดรูปแบบทั้งก้อน** เป็นบั๊กของแอป เครื่องหยุดส่ง แสดงสถานะผิดพลาด และเก็บคิวไว้ครบ
- **เมื่อ server ตอบว่าประวัติไม่ตรง** ทำตามข้อ 8.10

view ของแต่ละแถวคือค่าใน base ที่ถูกทับด้วย op ของทุก mutation ใน pending ตามลำดับ นี่คือการ rebase: เมื่อ base เปลี่ยน ค่าที่ผู้ใช้เพิ่งแก้ยังแสดงอยู่ และเพราะ mutation ออกจาก pending ก็ต่อเมื่อผลของมันอยู่ใน base แล้ว ค่าที่แสดงจึงไม่ย้อนกลับไปเป็นค่าเก่าชั่วขณะ

### 8.4 กติกาการตรวจและเมื่อแก้ชนกัน

| กรณี | ผล |
|---|---|
| สองคนแก้ฟิลด์เดียวกันของแถวเดียวกัน | คนที่ถึง server ทีหลังชนะ |
| สองคนแก้คนละฟิลด์ของแถวเดียวกัน | ได้ทั้งสองอย่าง |
| คนหนึ่งแก้ อีกคนย้ายลงถังขยะ | ได้ทั้งสองอย่าง แถวอยู่ในถังขยะพร้อมค่าที่แก้ |
| อ้างถึงสิ่งที่อยู่ในถังขยะ เช่น ย้าย issue เข้า project ที่ถูกย้ายลงถังขยะ | รับ สิ่งที่อยู่ในถังขยะถือว่ายังมีอยู่ |
| อ้างถึงสิ่งที่ไม่เคยมี | ปฏิเสธ |
| มอบงานให้สมาชิกที่ถูกถอดแล้ว | ปฏิเสธ งานเดิมของคนนั้นยังคงชื่อไว้ |
| สร้างแถวด้วย id ที่มีอยู่แล้ว | ปฏิเสธ ยกเว้น IssueLabel |
| ติด label ที่ติดอยู่แล้ว หรือสองคนติด label เดียวกัน | รับ และมีแถวเชื่อมแถวเดียว |
| สองคนติด label คนละอันให้ issue เดียวกัน | ได้ทั้งสองอัน |
| คนหนึ่งติด อีกคนถอด label เดียวกัน | คนที่ถึง server ทีหลังชนะ |
| แก้รายละเอียดของ issue โดยอิงฉบับที่ไม่ใช่ล่าสุด | ปฏิเสธ (ดูด้านล่าง) |
| แก้รายละเอียดต่อจากการบันทึกของตัวเองที่ยังรอผลอยู่ | รับ ถ้าฉบับล่าสุดบน server มาจากการบันทึกนั้น |

รายละเอียดของ issue **[ข้อเสนอ]**:

- บันทึกเมื่อผู้ใช้กดบันทึกหรือออกจากช่อง ไม่บันทึกทุกตัวอักษร และเป็น mutation ของตัวเองเสมอ ไม่รวมกับ op อื่น ยกเว้นข้อความเริ่มต้นที่มากับการสร้าง issue
- คำสั่งแก้รายละเอียดต้องบอกฉบับที่ผู้ใช้เริ่มแก้ ซึ่งเป็นได้สองแบบ
  - rev ของฉบับใน base
  - `uid` ของการบันทึกครั้งก่อนของเครื่องนี้ที่ยังอยู่ใน pending ใช้เมื่อผู้ใช้บันทึกซ้ำก่อนที่ผลของครั้งก่อนจะกลับมา ซึ่งเกิดเสมอเมื่อบันทึกหลายครั้งตอน offline
- server รับเมื่อ rev ตรงกับค่าปัจจุบัน หรือเมื่อ delta ที่สร้าง rev ปัจจุบันมีที่มาเป็น `uid` ที่อ้าง นอกนั้นปฏิเสธ
- เมื่อถูกปฏิเสธด้วยเหตุนี้ เครื่องแสดงข้อความของผู้ใช้คู่กับฉบับล่าสุด ให้ผู้ใช้รวมเองแล้วบันทึกใหม่ จึงไม่มีข้อความของใครถูกทับโดยที่ผู้ทับไม่เคยเห็น
- หัวข้อของ issue ใช้กติกาปกติ คือคนที่ถึงทีหลังชนะ
- ยกระดับได้ภายหลังด้วย CRDT เฉพาะฟิลด์นี้

การแก้หลายรายการพร้อมกัน: mutation หนึ่งชุดมีได้ไม่เกิน 50 op การแก้ที่มากกว่านั้นถูกแบ่งเป็นหลายชุด ซึ่งสำเร็จหรือล้มเหลวแยกกัน ชุดที่ล้มเหลวปรากฏในรายการที่ไม่สำเร็จ

### 8.5 โหลดครั้งแรก, pull และ poke

**โหลดครั้งแรก (bootstrap)**

- server ต้องอ่านตำแหน่งล่าสุดของ workspace **ก่อน** อ่านแถวใดของข้อมูล แล้วตอบตำแหน่งนั้นในหน้าแรก พร้อมเลข mutation ล่าสุดที่ประมวลผลแล้วของ client นี้ ลำดับนี้สำคัญ: ถ้าอ่านแถวก่อน การแก้ไขที่ commit คั่นกลางจะไม่อยู่ทั้งในหน้าที่อ่านและใน delta ที่จะดึงตามมา
- การแบ่งหน้าต้องไล่ตาม primary key ที่ไม่เปลี่ยน ห้ามใช้ลำดับที่หรือคอลัมน์ที่เปลี่ยนค่าได้ และจำกัดขนาดหน้าด้วยจำนวนไบต์
- เมื่อได้ครบทุกหน้า เครื่อง pull ตั้งแต่ตำแหน่งที่หน้าแรกบอก และใช้ delta ทับตามลำดับ วิธีนี้ถูกต้องแม้มีคนแก้ระหว่างโหลด เพราะ delta บรรจุแถวทั้งแถวในสภาพหลังเปลี่ยน
- UI เริ่มใช้ข้อมูลได้เมื่อขั้นตอนทั้งหมดเสร็จเท่านั้น

**Pull**

- เครื่องส่งตำแหน่งของตน server ตรวจตำแหน่งก่อน ถ้าไม่ตรงให้ตอบว่า "ประวัติไม่ตรง"
- server ตอบ delta ที่อยู่หลังตำแหน่งนั้นเรียงตามลำดับ จำกัดด้วยจำนวนไบต์โดยมีอย่างน้อยหนึ่ง delta พร้อมบอกว่ายังมีอีกหรือไม่
- เพราะ `syncId` ถูกออกภายใต้ล็อกและ commit ตามลำดับ ผู้อ่านจึงไม่มีวันเห็นเลขที่ข้าม แล้วมีเลขตรงกลางโผล่ตามมาทีหลัง
- ถ้าเครื่องตามหลังมากเกินกว่าที่ pull จะคุ้ม ให้ bootstrap ใหม่โดยไม่แตะ pending

**Poke**

- การสะกิดเปิดหรือปิดได้ต่อ deployment server บอกเครื่องว่าเปิดอยู่หรือไม่ และควรดึงเป็นรอบถี่แค่ไหน เมื่อปิด เครื่องดึงตามรอบเวลาอย่างเดียว
- เมื่อเปิด เครื่องเปิด WebSocket หนึ่งเส้นต่อ workspace server ส่งข้อความสั้นที่มีแค่ `syncId` ล่าสุดเมื่อมีการ commit และส่งสัญญาณชีพเป็นระยะ
- การสะกิดเดินทางระหว่าง server ด้วย LISTEN กับ NOTIFY ของ Postgres ซึ่งแม่แบบใช้อยู่แล้ว เนื้อหาของ NOTIFY มีแค่ workspace กับ `syncId`
- ข้อความสะกิดไม่มีข้อมูลงาน ข้อมูลทุกชิ้นได้จาก pull ซึ่งตรวจสิทธิ์ทุกครั้ง
- เมื่อการเชื่อมต่อหลุด เครื่องเชื่อมต่อใหม่แบบหน่วงเวลาเพิ่มขึ้นพร้อมสุ่ม แล้ว pull หนึ่งครั้ง
- เมื่อ server ต่อ LISTEN ใหม่ ให้ปิด WebSocket ทั้งหมดของตัวเอง เพื่อให้ทุกเครื่องเชื่อมต่อใหม่แล้ว pull ตามแบบที่แม่แบบทำอยู่
- **เมื่อแท็บถูกซ่อนหรือไม่มีการใช้งานเกิน 5 นาที** เครื่องปิด WebSocket และหยุดดึงตามรอบ แล้วกลับมาเชื่อมต่อและ pull เมื่อผู้ใช้กลับมา เพื่อไม่ให้แท็บที่เปิดทิ้งไว้ใช้ทรัพยากรของ server
- UI แสดงสถานะการเชื่อมต่อและจำนวนรายการที่รอส่งเสมอ

**เชื่อมต่อใหม่หลังขาดการติดต่อ**

1. Push ทุกรายการใน pending ตามลำดับ server ตอบผลเดิมสำหรับรายการที่เคยประมวลผลแล้ว และประมวลผลรายการที่เหลือ
2. Pull จนทัน
3. mutation ออกจาก pending ตามสามกรณีในข้อ 8.3

### 8.6 ตัวตนของ client และเลขของ mutation **[ข้อเสนอ]**

เลขของ mutation ต้องไม่ถูกใช้ซ้ำ ไม่ว่าแท็บจะถูก reload, ถูกทำสำเนา หรือเบราว์เซอร์ล้มกลางคัน

- sync client หนึ่งตัวถูกสร้างด้วย workspace, ผู้ใช้ และ **ชื่ออุปกรณ์** ซึ่งมีค่าตั้งต้นค่าเดียว ชื่ออุปกรณ์แยกที่เก็บในเครื่อง, ล็อกของแท็บ และตัวตนของ client ออกจากกัน หน้าเดโมใช้สองชื่อเพื่อแสดงสองฝั่งในหน้าเดียว
- **ก่อน M3 (ยังไม่มีที่เก็บในเครื่อง)** sync client ทุกตัวที่ถูกสร้างได้ `clientId` ใหม่ และนับ `mutationId` ในหน่วยความจำ แต่ละแท็บจึงเป็น client อิสระที่ทำงานสดพร้อมกันได้ pending หายเมื่อปิดหรือ reload จึงต้องเตือนก่อนออกจากหน้าเมื่อยังมีรายการค้าง
- **ตั้งแต่ M3** มี client ถาวรหนึ่งตัวต่อเบราว์เซอร์ ต่อ workspace ต่อผู้ใช้ ต่อชื่ออุปกรณ์ `clientId` กับตัวนับเลขถัดไปเก็บใน IndexedDB
  - การออก `mutationId` กับ `uid` และการเขียน mutation ลง outbox ต้องอยู่ใน transaction เดียวของ IndexedDB
  - ส่ง mutation ได้ก็ต่อเมื่อ transaction นั้นสำเร็จแล้วเท่านั้น
  - ห้ามเก็บตัวตนของ client ในที่ที่เบราว์เซอร์ทำสำเนาให้แท็บอื่นได้ เช่น sessionStorage

### 8.7 การเก็บในเครื่อง (M3)

IndexedDB หนึ่งฐานต่อ workspace ต่อผู้ใช้ ต่อชื่ออุปกรณ์ มีส่วนเหล่านี้: แถวของ base, ค่ากำกับ (ตำแหน่ง, เวอร์ชันของ protocol, ตัวตนของ client และตัวนับ, เวลาที่ติดต่อ server สำเร็จครั้งล่าสุด), outbox และรายการที่ไม่สำเร็จ

กติกาการเขียน ซึ่งต้องถูกต้องแม้มีสองแท็บเขียนในเวลาใกล้กัน:

- **นำ delta ไปใช้** ใน transaction เดียว: ตรวจว่า `syncId` ต่อจากค่าที่เก็บไว้พอดี ถ้าใช่ให้เขียนแถวและปรับตำแหน่ง ถ้าค่าที่เก็บไว้ถึงแล้วให้ข้ามการเขียนแถว ถ้าค่าที่เก็บไว้ยังตามหลังเกินหนึ่ง ให้ยกเลิกแล้วเขียน delta ที่ขาดตามลำดับก่อน จากนั้นลบรายการใน outbox ที่ที่มาของ delta ระบุถึงเสมอ ไม่ว่ารอบนี้จะได้เขียนแถวหรือไม่
- **ถูกปฏิเสธ** ใน transaction เดียว: ย้ายรายการจาก outbox ไปยังรายการที่ไม่สำเร็จ รายการที่ไม่สำเร็จอยู่จนกว่าผู้ใช้จะส่งใหม่หรือทิ้ง
- **bootstrap** เขียนลงพื้นที่พักก่อน แล้วสลับเป็น base เมื่อครบและไล่ delta ทันแล้ว base ที่เขียนไม่ครบต้องไม่ถูกนำมาใช้
- เปิดแอปครั้งถัดไป แสดงข้อมูลจากเครื่องก่อน แล้วตามให้ทันด้วย pull
- การแก้ไขล่าสุดอาจหายได้ถ้าเบราว์เซอร์ถูกปิดในไม่กี่มิลลิวินาทีก่อนเขียนลง outbox เสร็จ ในกรณีนั้นยังไม่มีอะไรถูกส่ง ข้อมูลจึงไม่เพี้ยน ยอมรับข้อจำกัดนี้
- ทางหนีเมื่อสำเนาในเครื่องมีปัญหา: ปุ่มล้างสำเนาแล้วโหลดใหม่ โดยไม่แตะ outbox และรายการที่ไม่สำเร็จ

### 8.8 หลายแท็บ (M3) **[ข้อเสนอ]**

- สำหรับชื่ออุปกรณ์หนึ่งในเบราว์เซอร์หนึ่ง มีแท็บเดียวที่เป็น **ตัวทำงาน** คือถือ WebSocket, push และนำ delta ไปใช้ เลือกด้วย Web Locks
- แท็บที่ผู้ใช้กำลังใช้อยู่แย่งสิทธิ์มาเป็นตัวทำงานเสมอ แท็บที่เสียสิทธิ์ปิด WebSocket หยุด push และ pull แสดงเครื่องหมายว่าหยุดชั่วคราว และรอคิวรับสิทธิ์คืนเมื่อแท็บตัวทำงานถูกปิด
- แท็บที่ได้สิทธิ์โหลด base, outbox และรายการที่ไม่สำเร็จจาก IndexedDB ใหม่ทั้งหมด แล้วทำงานต่อด้วย client ถาวรตัวเดิม การแก้ไขที่ค้างส่งจากแท็บก่อนหน้าจึงปรากฏในแท็บใหม่ทันที แม้ยังไม่มีเน็ต
- ทุกแท็บเขียน mutation ลง outbox ได้ทันทีโดยไม่ต้องรอได้สิทธิ์ เพราะการออกเลขอยู่ใน transaction ของ IndexedDB เมื่อเขียนแล้วต้องแจ้งแท็บอื่น ตัวทำงานจะโหลดรายการใหม่ไปส่ง
- แท็บที่เพิ่งเสียสิทธิ์อาจยังทำงานค้างอยู่ชั่วครู่ ความถูกต้องต้องไม่ขึ้นกับว่ามันหยุดทันที กติกาที่รองรับคือ การออกเลขใน transaction, การตรวจ `syncId` ก่อนเขียน base และการเลื่อนเลขแบบมีเงื่อนไขที่ server
- ข้อจำกัดที่ยอมรับ: หน้าต่างที่ไม่ได้ถูกเลือกจะไม่อัปเดตสด

### 8.9 เปิดแอปขณะไม่มีเน็ต (M3) **[ข้อเสนอ]**

- ใช้ service worker เก็บไฟล์ของแอปไว้ในเครื่อง แอปจึงเปิดได้และแสดงข้อมูลจากเครื่องโดยไม่มีเน็ต
- ข้อมูลในเครื่องแสดงได้โดยไม่ตรวจ session กับ server แต่ถ้าเครื่องไม่ได้ติดต่อ server สำเร็จเกิน 30 วัน ซึ่งเท่ากับอายุของ session ต้อง login แบบออนไลน์ก่อนจึงแสดงข้อมูล
- เมื่อต้องเปลี่ยนเวอร์ชัน (ข้อ 8.10) ต้องอัปเดต service worker ให้เสร็จก่อนโหลดหน้าใหม่ ห้ามวนโหลดแอปรุ่นเก่าจากที่เก็บไว้ซ้ำ ๆ

### 8.10 เวอร์ชัน และเมื่อประวัติไม่ตรง

**เวอร์ชันของ protocol**

- ทุก request บอกเวอร์ชันของ protocol ที่เครื่องใช้ และ mutation แต่ละชุดจำเวอร์ชันที่สร้าง
- **Pull กับ bootstrap** ต้องเป็นเวอร์ชันเดียวกับ server ถ้าไม่ตรง server ปฏิเสธพร้อมบอกเวอร์ชันของตัวเอง
- **Push** server รับ mutation ของเวอร์ชันปัจจุบันและเวอร์ชันก่อนหน้าหนึ่งรุ่น โดย server เป็นผู้แปลง เครื่องไม่แก้เนื้อหาของ mutation ที่ออกเลขแล้ว แท็บรุ่นเก่าจึงส่งคิวที่ค้างให้หมดได้ก่อนเปลี่ยนรุ่น
- **เมื่อ server ใหม่กว่าเครื่อง** เครื่อง push คิวที่ค้างให้หมดก่อน แล้วจึงโหลดแอปรุ่นใหม่ ทิ้ง base และ bootstrap ใหม่ ก่อน M3 ห้ามโหลดหน้าใหม่เองขณะ pending ยังไม่ว่าง ให้แสดงปุ่มและให้ผู้ใช้ตัดสิน
- **mutation ที่เก่ากว่าเวอร์ชันก่อนหน้า** ซึ่งเกิดได้เมื่อเครื่อง offline ข้ามการเปลี่ยนสองรุ่น ส่งตามเดิมไม่ได้ ให้ทำตามกติกาหลักในข้อ 8.3 คือส่งเป็น mutation ว่างและย้ายเนื้อหาไปยังรายการที่ไม่สำเร็จ
- **เมื่อ server เก่ากว่าเครื่อง** ซึ่งเกิดระหว่าง deploy ที่มี server สองรุ่นพร้อมกัน เครื่องรอแล้วลองใหม่ ห้ามโหลดหน้าใหม่วนไป
- migration ต้องเป็นแบบเพิ่มเท่านั้นภายในหนึ่งรุ่น เพื่อให้ server รุ่นเก่าที่ยังรันอยู่ระหว่าง deploy ทำงานกับฐานข้อมูลที่ถูก migrate แล้วได้
- หลัง migration แล้วถอย server กลับรุ่นเก่าไม่ได้ เพราะแม่แบบไม่ยอมเริ่มเมื่อเจอ migration ที่ไม่รู้จัก ทางแก้คือ deploy รุ่นที่แก้แล้ว หรือกู้คืนฐานข้อมูล
- มีเทสต์ที่ผูกรูปร่างของ op ในสัญญากับเลขเวอร์ชัน การแก้รูปร่างของ op โดยไม่เพิ่มเลขจึงทำให้เทสต์พัง
- กติกาเหล่านี้ต้องมีตั้งแต่ M1 เพราะแท็บที่เปิดค้างไว้เจอ deploy ใหม่ได้ตั้งแต่วันแรก

**เมื่อประวัติไม่ตรง**

เกิดเมื่อฐานข้อมูลถูกกู้คืนจากสำเนา หรือถูกล้าง server ตรวจพบเองจากตำแหน่งที่เครื่องส่งมา ไม่ต้องมีขั้นตอนที่คนต้องจำ เครื่องทำดังนี้:

1. Bootstrap ใหม่โดยไม่แตะ pending หน้าแรกบอกเลข mutation ล่าสุดที่ server ประมวลผลแล้วของ client นี้ เรียกว่า L
2. ลืมทุกอย่างที่จำไว้ว่ารับแล้ว
3. ถ้าเลขน้อยสุดใน pending มากกว่า L บวกหนึ่ง ให้ออกเลขใหม่ให้ pending ทั้งหมดต่อจาก L โดยคงลำดับและ `uid` เดิม ทำได้เพราะ server ที่ถูกกู้คืนไม่มีบันทึกของเลขที่สูงกว่า L ตั้งแต่ M3 ขั้นนี้ต้องอยู่ใน transaction เดียวของ IndexedDB
4. Push ทุกรายการใน pending ใหม่

สิ่งที่ต้องยอมรับ: การแก้ไขที่ server รับไปแล้วหลังจุดสำรอง และเครื่องนำไปใช้กับ base แล้ว จะหายไปพร้อมการกู้คืน ส่วนรายการที่ยังอยู่ใน pending ของเครื่องจะถูกส่งใหม่และไม่หาย

### 8.11 ทางลัดที่ตั้งใจ **[ข้อเสนอ]**

- ไม่ตัดบันทึกความเปลี่ยนแปลง และไม่ลบแถวในตาราง client ในรุ่นแรก ที่ขนาดนี้ข้อมูลโตช้า ต้องทบทวนเมื่อพื้นที่เข้าใกล้เพดานของที่ host
- สมาชิกทุกคนเห็นข้อมูลทั้ง workspace จึงไม่มีการแยกว่าใครได้รับ delta ไหน
- ไม่ส่ง delta ผ่าน WebSocket โดยตรง การสะกิดแล้ว pull ช้ากว่าหนึ่งรอบ request แต่ทำให้เส้นทางข้อมูลมีทางเดียวที่ตรวจสิทธิ์และอยู่ในสัญญา

## 9. Server บน RR stack

### 9.1 โครงตามแม่แบบ

- Lamdap เริ่มจาก `bun create rr-stack` แบบ prerender กับ SPA และ Tailwind
- โค้ดของ sync เป็นโมดูลใหม่ใน `server/src` ลงทะเบียนเส้นทางใน `api_router()` ตามแบบของแม่แบบ ทุกเส้นทางของ push, pull และ bootstrap มี `operation_id` และรายการ error ที่เป็นไปได้ จึงอยู่ใน `openapi.json` และได้ client ของ TypeScript มาเอง
- ข้อความสะกิดเป็น enum ของ Rust ที่ลงทะเบียนแบบเดียวกับที่แม่แบบทำกับข้อความ WebSocket ของตัวเอง type ของข้อความจึงอยู่ในสัญญา ส่วนเส้นทางของ WebSocket เองไม่อยู่ในสัญญา เหมือนในแม่แบบ
- type ของ model, op, mutation, ผลของ mutation และ delta เป็น struct กับ enum ของ Rust
- เนื้อหาของ op ถูกอ่านแบบผ่อนปรนที่ขอบแล้วตรวจทีละ mutation เพื่อให้เป็นไปตามข้อ 8.2 ขั้น 5 โดยสัญญายังระบุ type ของ op ครบ
- ใช้ `CurrentUser`, `AppJson`, `AppPath`, `AppQuery` และรูปแบบ error ของแม่แบบ
- หน้าตัวอย่างและโมดูล todo ของแม่แบบถูกถอดออกใน M1 เมื่อมีของ Lamdap มาแทน script `smoke` และงานของ CI ที่พึ่งการสมัครแบบเปิดกับ todo ต้องถูกเขียนใหม่ในคราวเดียวกัน

### 9.2 Postgres

- ตารางใหม่: workspace, สมาชิก, รหัสเชิญ, ตารางข้อมูลงานตามข้อ 7, บันทึกความเปลี่ยนแปลง, ตาราง client และผลการปฏิเสธ
- บันทึกความเปลี่ยนแปลงมี primary key เป็น workspace กับ `syncId` และมีข้อบังคับไม่ให้ `clientId` กับ `mutationId` คู่เดียวกันปรากฏสองครั้งใน workspace เดียว
- มีทางลงบันทึกทางเดียวในโค้ด ทุกจุดที่แก้ตารางที่ sync ต้องเรียกผ่านทางนั้น
- การล็อกในข้อ 8.2 เป็นการล็อกแถวภายใน transaction การรอล็อกมีเวลาจำกัด และ transaction ต้องสั้น ไม่รอ I/O อื่นนอกจากฐานข้อมูลขณะถือล็อก
- push ที่รอล็อกอยู่ต้องไม่ทำให้ pull ขาดการเชื่อมต่อฐานข้อมูล **[ผู้สร้าง เลือกวิธี]**
- การเชื่อมต่อสำหรับ LISTEN ถูกหยิบจาก pool และถือไว้ตลอด จำนวนการเชื่อมต่อที่ใช้งานได้จริงจึงน้อยกว่าขนาดของ pool หนึ่งเส้น ต้องตั้งขนาดของ pool โดยนับเส้นนี้ และจำนวนรวมของทุก server ต้องอยู่ในเพดานของฐานข้อมูล
- ระบบรองรับ server หลายตัวพร้อมกันโดยไม่มีสถานะสำคัญในหน่วยความจำ

### 9.3 เพดาน **[ผู้สร้าง ปรับได้]**

- mutation ไม่เกิน 50 op และ request ของ push ไม่เกิน 1 MB delta ที่ใหญ่ที่สุดจึงอยู่ใต้ขนาดของหน้าเสมอ ต้องมีการตรวจข้อนี้ในโค้ด
- หน้าของ bootstrap และ pull ไม่เกิน 1 MB เพื่อให้อยู่ใต้เพดาน 4.5 MB ของ Vercel อย่างปลอดภัย และคืนอย่างน้อยหนึ่งรายการเสมอ
- push หนึ่ง request มีงบเวลา
- จำกัดอัตราของ push ต่อผู้ใช้ ตัวจำกัดอัตราของแม่แบบนับตาม IP เท่านั้น จึงต้องขยายให้นับตามผู้ใช้ได้
- แต่ละ workspace มีตัวนับจำนวนไบต์ที่ลงบันทึกสะสม เมื่อเกินเพดาน ให้ปฏิเสธการสร้างและการแก้รายละเอียด พร้อมแจ้งผู้ใช้ ค่าเพดานกำหนดหลัง M0 ตามพื้นที่ของที่ host

### 9.4 ความคงทนของข้อมูลจริง **[ข้อเสนอ]**

- ข้อมูลใน workspace จริงถือว่าถาวรตั้งแต่ M1 ห้ามล้างเพื่อความสะดวกในการพัฒนา
- **สำรองระดับฐานข้อมูล** ใช้ความสามารถกู้คืนของที่ host ถ้ามี และ `pg_dump` ตามรอบ ขั้นตอนกู้คืนต้องเขียนไว้ และซ้อมจริงหนึ่งครั้งก่อนปิด M1 โดยมีเครื่องที่เปิดแอปค้างอยู่ เพื่อยืนยันว่าเครื่องโหลดใหม่เองตามข้อ 8.10
- **ส่งออก** ทั้ง workspace เป็นไฟล์ JSON จากข้อมูลในเครื่อง เป็นทางหนีสุดท้ายที่ผู้ใช้ถือข้อมูลของตัวเองได้
- ก่อน deploy ที่มี migration ต้องสำรองฐานข้อมูลก่อน

## 10. ความปลอดภัยและข้อมูลส่วนบุคคล

- **Login** ใช้ระบบของแม่แบบ: อีเมลกับรหัสผ่าน, hash ด้วย Argon2id, cookie แบบ HttpOnly, Secure, SameSite=Lax, เก็บเฉพาะ hash ของ token และจำกัดอัตราการ login
- **ระบบปิด [ข้อเสนอ]**
  - แม่แบบเปิดให้ใครก็สมัครได้และไม่ยืนยันอีเมล Lamdap ต้องปิดจุดนี้: สมัครได้เฉพาะเมื่อส่งรหัสเชิญที่ถูกต้อง
  - รหัสเชิญเป็นค่าสุ่มอย่างน้อย 128 บิต ใช้ได้ครั้งเดียว หมดอายุใน 7 วัน เก็บเฉพาะ hash และถูกใช้ไปในคำสั่งเดียวกับ transaction ที่สร้างผู้ใช้ รหัสผูกกับอีเมลหนึ่งอีเมลด้วย แต่ความปลอดภัยอยู่ที่ตัวรหัส เพราะระบบไม่ยืนยันอีเมล
  - ผู้ที่มีบัญชีอยู่แล้วเข้าร่วม workspace เพิ่มด้วยการใส่รหัสเชิญขณะ login อยู่
  - **เจ้าของระบบคนแรก** สมัครได้ด้วยรหัสตั้งต้นที่เป็น secret ของ production และใช้ได้ครั้งเดียว ไม่ใช้การจับคู่อีเมลอย่างเดียว เพราะอีเมลของเจ้าของเห็นได้จากประวัติ commit ของ repo สาธารณะ
  - สร้าง workspace ได้เฉพาะเจ้าของระบบ เชิญและถอดสมาชิกได้เฉพาะ owner ของ workspace
  - เจ้าของระบบออกรหัสตั้งรหัสผ่านใหม่แบบใช้ครั้งเดียวให้สมาชิกที่ลืมรหัสผ่านได้
- **WebSocket ของการสะกิด** แม่แบบไม่ตรวจตัวตนและไม่ตรวจต้นทาง เพราะข้อมูลของแม่แบบเป็นสาธารณะ Lamdap ต้องตรวจ session, ตรวจสมาชิกภาพ และตรวจว่าคำขอมาจากต้นทางเดียวกัน ด้วยกติกา `Sec-Fetch-Site` แบบที่แม่แบบใช้กับ logout ร่วมกับการเทียบ Origin กับ host ของ request เอง
- **คำขอที่เปลี่ยนข้อมูล** แม่แบบพึ่ง SameSite=Lax กับการบังคับ content type เป็น JSON Lamdap เพิ่มการตรวจต้นทางแบบเดียวกันกับทุกคำขอที่เปลี่ยนข้อมูล
- **ไม่เชื่อเครื่องผู้ใช้** ทุก mutation ถูกตรวจสิทธิ์และตรวจข้อมูลที่ server และ `clientId` ผูกกับผู้ใช้คนเดียว คนอื่นส่งในนามไม่ได้
- **Markdown** แสดงผลโดยไม่อนุญาต HTML ดิบ และอนุญาตเฉพาะลิงก์ `http`, `https`, `mailto`
- **ข้อมูลในเครื่อง** แยกฐานตามผู้ใช้
  - เมื่อ logout ให้ล้างข้อมูลในเครื่องของผู้ใช้นั้น โดยเตือนก่อนถ้ายังมีรายการรอส่ง
  - เมื่อ server ตอบว่าไม่ใช่สมาชิกของ workspace แล้ว ให้ล้างข้อมูลของ workspace นั้น โดยแจ้งจำนวนรายการที่ยังไม่ได้ส่ง
  - เมื่อ session หมดอายุ ไม่ล้างข้อมูล ให้ login ใหม่ แล้วทำงานต่อด้วยข้อมูลเดิม
- **ชนิดของระบบ** ฐานข้อมูลแต่ละชุดถูกบันทึกตอนตั้งค่าว่าเป็นระบบจริงหรือเดโม โหมดเดโมเปิดได้เมื่อทั้งค่าตั้งของ deployment และบันทึกนี้ระบุว่าเป็นเดโม งานล้างข้อมูลต้องตรวจบันทึกนี้ในคำสั่งเดียวกับที่ล้าง และยกเลิกถ้าไม่ใช่เดโม
- **ข้อมูลส่วนบุคคล** เก็บเท่าที่ต้องใช้ คืออีเมลกับชื่อที่แสดง เพื่อให้ภาระตาม PDPA น้อยที่สุด
- **Secret** ไม่อยู่ใน repo
- งานส่วนนี้ต้องผ่านการตรวจด้านความปลอดภัยโดยผู้ที่ไม่ใช่ผู้เขียนโค้ดส่วนนั้น รายการตรวจคือทุกหัวข้อในข้อนี้ แต่ละหัวข้อต้องมีเทสต์หรือหลักฐานการตั้งค่า

## 11. หน้าจอและระบบคีย์บอร์ด

```
┌ Lamdap ─────┬ Issues ──────────────── ● ออนไลน์ ── Ctrl+K ┐
│ Issues      │ In progress                                  │
│ Board       │  ● สูง   LMD-12  แก้หน้า login       @คุณ     │
│ Projects    │ Todo                                         │
│  ▸ Web app  │  ○ กลาง  LMD-14  เพิ่ม board view    @เพื่อน   │
│  ▸ API      │  ○ ต่ำ   LMD-…   เขียน README (รอส่ง) —       │
│ Trash       │                                              │
└─────────────┴──────────────────────────────────────────────┘
```

หน้าจอ:

- รายการ issue จัดกลุ่มตามสถานะ กรองตามผู้รับผิดชอบ, project, label, ความสำคัญ และค้นหาด้วยข้อความ
- Board แบ่งคอลัมน์ตามสถานะ ลากวางได้ และย้ายด้วยคีย์บอร์ดได้
- หน้า issue (รวมหน้าจอเลือกระหว่างข้อความของตนกับฉบับล่าสุดเมื่อแก้รายละเอียดชนกัน), หน้า project, ถังขยะ
- ตั้งค่า: สมาชิกและการเชิญ, label, ชื่อและ key ของ workspace, ส่งออกข้อมูล
- ตัวบอกสถานะ: การเชื่อมต่อ, จำนวนรายการที่รอส่ง, server บันทึกไม่ได้ชั่วคราว, แท็บนี้หยุดชั่วคราว, มีเวอร์ชันใหม่, sync ผิดพลาดและหยุดส่ง
- รายการที่ไม่สำเร็จ พร้อมปุ่มส่งใหม่และทิ้ง

ระบบคีย์บอร์ด:

- มีทะเบียนคำสั่งที่เดียว ใช้ร่วมกันทั้ง command palette, คีย์ลัด และหน้ารวมคีย์ลัด
- คำสั่งรู้บริบท เช่น มี issue ถูกเลือกอยู่หรือไม่ และคีย์ลัดตัวอักษรเดี่ยวไม่ทำงานขณะพิมพ์ในช่องข้อความ
- ทุกอย่างในขอบเขตรุ่นแรกทำได้โดยไม่ใช้เมาส์
- **คีย์ลัดต้องทำงานเมื่อแป้นพิมพ์อยู่ที่ภาษาไทย** จึงต้องอ่านตำแหน่งปุ่มจริง ไม่ใช่ตัวอักษรที่พิมพ์ออกมา

ภาษาและการแสดงผล **[ข้อเสนอ]**:

- ตัวหนังสือของ UI เป็นภาษาอังกฤษ
- เนื้อหาภาษาไทยต้องแสดงถูกต้อง แม่แบบมีฟอนต์ IBM Plex Sans Thai มาให้แล้ว ต้องตั้งระยะบรรทัดไม่ให้ตัดวรรณยุกต์ ค้นหาข้อความไทยได้ และเรียงลำดับตามหลักภาษาไทย
- วันที่แสดงตามภาษาของเบราว์เซอร์

ข้อกำหนดเชิงโครงสร้าง:

- หน้าของแอปเป็นเส้นทางแบบ SPA ของ React Router ไม่มี loader ที่รันบน server ข้อมูลงานทั้งหมดมาจาก sync client ไม่ผ่าน TanStack Query ส่วนสิ่งที่ไม่ใช่ข้อมูล sync เช่น login และการเชิญ ใช้ client ที่สร้างจากสัญญาตามปกติ
- UI ต้องสร้างได้มากกว่าหนึ่งชุดในหน้าเดียว โดยแต่ละชุดผูกกับ sync client ของตัวเอง ห้ามมีสถานะรวมศูนย์ที่มีได้ชุดเดียว เพราะเดโมแสดงสองฝั่งในหน้าเดียวกัน
- การค้นหาและการส่งออกทำในเครื่องทั้งหมด เพราะเครื่องมีข้อมูลครบอยู่แล้ว

หน้าตาและเอกลักษณ์ของแอปยังไม่กำหนดในเอกสารนี้ เจ้าของจะเลือกจาก mockup ใน M0 แล้วแทนค่า token ของธีมที่มากับแม่แบบ และต้องไม่เหมือน Linear

การเข้าถึง: โฟกัสมองเห็นได้ องค์ประกอบมี role ที่ถูกต้อง และความต่างสีผ่านเกณฑ์ WCAG AA

## 12. เดโมสาธารณะ **[ข้อเสนอ]**

- เดโมเป็น deployment แยกจากระบบจริง มีฐานข้อมูลของตัวเอง และถ้าอยู่บน Vercel ต้องอยู่คนละทีมกับระบบจริงและกับโปรเจกต์อื่นของเจ้าของ เพราะเมื่อโควตาหมด Vercel หยุดทุก deployment ของทีมนั้น
- ใช้โค้ดชุดเดียวกับระบบจริง โหมดเดโมเปิดตามกติกาชนิดของระบบในข้อ 10
- ปุ่ม "ลองเล่นเดโม" สร้างผู้ใช้แขกหนึ่งคนกับ workspace ตัวอย่างหนึ่งอัน โดยไม่ต้องกรอกอะไร ข้อมูลตัวอย่างถูกใส่ผ่านทางลงบันทึกปกติ
- หน้าเดโมแสดง sync client สองตัวของแขกคนเดียวกันคู่กันในหน้าเดียว โดยใช้ชื่ออุปกรณ์ต่างกันตามข้อ 8.6 จึงเหมือนใช้สองเครื่อง แก้ฝั่งหนึ่งแล้วเห็นอีกฝั่งเปลี่ยน
- แต่ละฝั่งมีสวิตช์ตัดเน็ตของตัวเอง จึงลองแก้ตอน offline, แก้ชนกัน และต่อกลับได้
- แผงแสดงการ sync ของแต่ละฝั่ง: ตำแหน่ง, คิวที่รอส่ง, สถานะการเชื่อมต่อ และผลของ mutation ล่าสุด
- เดโมเปิดการสะกิด เพราะการใช้งานแต่ละครั้งสั้น และกติกาปิดการเชื่อมต่อเมื่อแท็บถูกซ่อนในข้อ 8.5 จำกัดการใช้ทรัพยากร
- ฐานข้อมูลของเดโมถูกล้างทุกวันด้วยงานตามเวลา ซึ่งตรวจชนิดของระบบก่อนล้างเสมอ
- การสร้างแขกถูกจำกัดอัตราต่อ IP และแต่ละ workspace ของเดโมมีเพดานจำนวน issue กับจำนวน mutation **[ผู้สร้าง กำหนดค่า]**

## 13. Repo และการทำงานสองคน

โครงสร้างเป็นของ RR stack โดยเพิ่มส่วนของ Lamdap:

| ที่ | หน้าที่ | ผู้ดูแล |
|---|---|---|
| `server/` | API ของ Rust, migration และเทสต์ รวมโมดูล sync | เจ้าของ |
| `web/app/sync/` | sync client เป็น TypeScript ล้วน ไม่พึ่ง React | เจ้าของ |
| ตัวจำลอง และ script `bun run sim` | อยู่นอกชุดเทสต์ที่ `bun run check` รัน เพราะต้องมี server จริง | เจ้าของ |
| `web/app/routes/`, `web/app/components/`, `web/app/app.css` | หน้าจอ, ระบบคีย์บอร์ด, ธีม | jxyluvcode |
| `web/e2e/` | เทสต์เบราว์เซอร์ของแต่ละ flow | คนที่ทำ flow นั้น |
| `web/app/api/`, `openapi.json`, `server/.sqlx/` | สร้างจากคำสั่ง ห้ามแก้ด้วยมือ | ไม่มี เปลี่ยนตาม PR ที่แก้ server |
| `scripts/`, ไฟล์ของ Docker และ CI | เครื่องมือของ stack | เจ้าของ |
| `docs/design` | เอกสารออกแบบ และแผนงานใน `docs/design/plans` | ร่วมกัน |

สัญญาระหว่างสองคนมีสองชั้น:

1. **`openapi.json`** สำหรับทุกอย่างที่คุยกับ server
2. **สัญญาของ sync client** ที่ UI ใช้ มี 4 อย่าง: อ่านข้อมูลแบบติดตามการเปลี่ยนแปลง, ส่งคำสั่งแก้ไข, อ่านสถานะ และอ่านกับจัดการรายการที่ไม่สำเร็จ รวมถึงข้อมูลสำหรับหน้าจอแก้รายละเอียดชนกัน การสร้าง sync client รับ workspace, ผู้ใช้ และชื่ออุปกรณ์

M0 ต้องส่งมอบสัญญาชั้นที่สองพร้อมตัวที่ทำงานได้ในหน่วยความจำ เพื่อให้งานหน้าจอเริ่มได้โดยไม่รอ engine ตัวจริง

วิธีทำงาน:

- `main` ถูกป้องกัน ทุกการเปลี่ยนแปลงเข้าผ่าน PR และ CI ของแม่แบบต้องผ่าน
- งานที่แก้ sync ทั้งฝั่ง server และฝั่งเครื่อง ถือว่าเสร็จเมื่อ `bun run check` และ `bun run sim` ผ่านทั้งคู่
- การแก้สัญญาทั้งสองชั้นต้องให้ทั้งสองคนเห็นชอบ เพราะกระทบทั้งสองฝั่ง
- model และกติกาฝั่ง server ทั้งหมดของรุ่นแรกทำให้เสร็จใน M1 เพื่อให้ M2 เป็นงานหน้าจอล้วน และ M3 เป็นงาน engine ล้วน
- การ merge เข้า `main` และการ deploy ต้องให้เจ้าของสั่ง

สิ่งที่ Lamdap ต้องเพิ่มหรือพบว่าต่างจากที่แม่แบบบอก ให้จดไว้ใน `docs/design/rr-stack-feedback.md` เพื่อนำกลับไปปรับปรุง stack รายการตั้งต้นจากการอ่านแม่แบบ:

- WebSocket ของแม่แบบไม่ตรวจตัวตนและไม่ตรวจต้นทาง
- หมายเหตุในโค้ดบอกว่าการเชื่อมต่อของ LISTEN เพิ่มจาก pool แต่จริง ๆ ถูกหยิบจาก pool
- ตัวจำกัดอัตรานับตาม IP เท่านั้น
- `smoke`, งานของ CI และ `e2e --url` พึ่งการสมัครแบบเปิด จึงใช้กับระบบปิดไม่ได้โดยไม่แก้
- ไม่มีชั้นจับ panic

## 14. การทดสอบ: หลักฐานว่า engine ถูกต้อง

### เทสต์ของ server

เทสต์ของ Rust ใช้ฐานข้อมูลจริงแบบที่แม่แบบทำ คือฐานใหม่ต่อเทสต์ ครอบคลุม:

- กติกาทุกแถวในข้อ 8.4
- การตอบซ้ำ, เลขซ้ำที่ `uid` ต่าง, ช่องว่างของเลข, mutation ว่าง, mutation ที่ผิดรูปแบบกลาง request
- **สอง request ของ mutation เดียวกันวิ่งพร้อมกันบนสองการเชื่อมต่อ** ต้องได้ผลเดียว ทั้งกรณีที่ทั้งคู่จะรับ และกรณีที่ฝั่งหนึ่งล้มแล้วพยายามบันทึกเป็นการปฏิเสธ
- โค้ดที่ panic ระหว่างประมวลผลถูกบันทึกเป็นการปฏิเสธ และ mutation ถัดไปยังเดินได้
- ความล้มเหลวชั่วคราวไม่ถูกบันทึกเป็นการปฏิเสธ
- mutation ที่ส่งพร้อมกันหลายเส้นเข้า workspace เดียว ต้องได้ `syncId` ต่อเนื่องไม่มีเลขข้าม และผู้อ่านที่ pull ระหว่างนั้นไม่เห็นเลขข้าม
- bootstrap ระหว่างมีการเขียน แล้ว pull ต่อ ต้องได้ข้อมูลเท่ากับ server
- ข้อมูลที่ได้จาก bootstrap ณ ตำแหน่งล่าสุด ต้องเท่ากับผลของการไล่บันทึกทั้งหมดตั้งแต่ต้น
- การตรวจตำแหน่ง: ตำแหน่งที่ไม่มีอยู่ และตำแหน่งที่ป้ายไม่ตรง ได้คำตอบว่าประวัติไม่ตรง
- สอง server บนฐานข้อมูลเดียว: commit ที่ตัวหนึ่งทำให้เครื่องที่ต่อกับอีกตัวถูกสะกิด
- สิทธิ์: คนนอก workspace, สมาชิกที่ถูกถอด, `clientId` ของคนอื่น, WebSocket จากต้นทางอื่น, การสมัครโดยไม่มีรหัสเชิญ, รหัสเชิญที่ใช้แล้ว, งานล้างข้อมูลบนระบบที่ไม่ใช่เดโม
- push ของเวอร์ชันก่อนหน้า และ pull ของเวอร์ชันที่ไม่ตรง
- เทสต์ที่ผูกรูปร่างของ op กับเลขเวอร์ชัน

### ตัวจำลอง

รัน sync client หลายตัวกับ **server จริงหนึ่งตัวที่รันบนฐานข้อมูลทดสอบ** ด้วยตัวสุ่มที่กำหนด seed ได้ ที่เก็บในเครื่องและช่องทางส่งของเครื่องเป็นตัวจำลองที่ควบคุมได้ การกระทำของผู้ใช้แต่ละครั้งมีรหัสซ่อนของตัวเอง เพื่อใช้ตรวจว่าสิ่งที่ server รับตรงกับสิ่งที่เครื่องบอกผู้ใช้ ตัวจำลองส่ง request ทีละรายการตามลำดับที่สุ่มได้ เพื่อให้รันซ้ำแล้วได้ผลเดิม การชนกันจริงของ request จึงทดสอบในเทสต์ของ server

ความผิดปกติที่ต้องสุ่มใส่:

- request ที่หาย ทั้งก่อนถึง server และหลัง server ประมวลผลแล้วแต่คำตอบไม่ถึงเครื่อง
- การหน่วง, การส่งซ้ำ, ช่วง offline, การสะกิดที่หายและที่ซ้ำ, การปิดการสะกิดทั้งหมด
- bootstrap ระหว่างมีคนแก้
- server หยุดแล้วเริ่มใหม่
- **ฐานข้อมูลถูกกู้คืนไปยังจุดก่อนหน้าขณะที่เครื่องยังเปิดอยู่**
- เวอร์ชันไม่ตรงกัน
- ตั้งแต่ M3: client ล้มและเริ่มใหม่ ณ ทุกจุดระหว่างออกเลข, เขียน outbox, ส่ง และรู้ผล
- ตั้งแต่ M3: การสลับแท็บตัวทำงานกลางคัน โดยตัวเก่ายังทำงานค้างอยู่ชั่วครู่ และการเขียน outbox จากแท็บที่ไม่ใช่ตัวทำงาน

สิ่งที่ต้องเป็นจริงทุก seed:

- **I1 ลงเอยตรงกัน** เมื่อทุกเครื่องเชื่อมต่อและคิวว่าง view ของทุกเครื่องเท่ากับข้อมูลของ server
- **I2 ไม่หาย ไม่ซ้ำ และไม่หลอก** การกระทำของผู้ใช้ทุกครั้งจบแบบใดแบบหนึ่งพอดี คือถูก server นำไปใช้หนึ่งครั้ง หรืออยู่ในรายการที่ไม่สำเร็จของเครื่อง ชุดที่ server นำไปใช้ต้องเท่ากับชุดที่เครื่องถือว่าถูกรับ ข้อยกเว้นเดียวคือการแก้ไขที่หายไปพร้อมการกู้คืนตามที่ระบุในข้อ 8.10
- **I3 เดินหน้าอย่างเดียว** ตำแหน่งของเครื่องไม่ถอยหลัง เว้นแต่ server ตอบว่าประวัติไม่ตรง และ delta ถูกใช้ตามลำดับโดยไม่ข้าม
- **I4 เห็นของตัวเอง** view ของเครื่องสะท้อน mutation ที่ยังรออยู่ของเครื่องนั้นเสมอ
- **I5 ทั้งชุดหรือไม่เลย** ไม่มี view ใดเห็น mutation เพียงบางส่วน
- **I6 ออกจากคิวถูกจังหวะ** mutation ออกจาก pending ด้วยสามกรณีในข้อ 8.3 เท่านั้น
- **I7 ไม่ค้าง** เมื่อการเชื่อมต่อนิ่งและ server ปกติ mutation ทุกชุดรู้ผลภายในจำนวนขั้นที่กำหนด รวมถึงหลังการกู้คืนฐานข้อมูล

เกณฑ์ขั้นต่ำ **[ผู้สร้าง ปรับขึ้นได้ ไม่ปรับลง]**: CI ของทุก PR รัน `bun run sim` อย่างน้อย 300 seed และพิมพ์ตัวนับว่าความผิดปกติแต่ละชนิดเกิดกี่ครั้ง แต่ละชนิดต้องเกิดอย่างน้อย 30 ครั้ง seed ที่ทำให้พังต้องพิมพ์ออกมาและรันซ้ำได้ มีรอบยาวที่รันตามเวลาแยกจาก CI ของ PR

### การทดสอบอื่น

- เทสต์หน่วยของ sync client ด้วยตัวรันเทสต์ของแม่แบบ
- End-to-end ด้วยตัวช่วยของแม่แบบ ซึ่งเปิดเบราว์เซอร์แยกกันสองตัวได้: คนหนึ่งแก้ อีกคนเห็น, แก้รายละเอียดชนกัน, บันทึกรายละเอียดสองครั้งติดกันตอน offline, ฉากไม่มีเน็ตตามเกณฑ์ของ M3, การสลับแท็บ, การใช้งานด้วยคีย์บอร์ด, คีย์ลัดขณะแป้นเป็นภาษาไทย, การตรวจการเข้าถึง
- เทสต์ที่ต้องสมัครผู้ใช้ทำผ่านทางปกติ คือสร้างเจ้าของระบบด้วยรหัสตั้งต้นของสภาพแวดล้อมทดสอบ แล้วให้เจ้าของระบบออกรหัสเชิญ ไม่มีทางลัดพิเศษสำหรับเทสต์
- `e2e` กับ deployment จริงรันกับเดโมเท่านั้น
- ความเร็วที่ข้อมูล 10,000 issue
- `bun run check`, `smoke` และ `e2e` รันใน CI ทุก PR ทั้งบน Linux และ Windows ตามแม่แบบ

## 15. Milestones

เอกสารนี้คือแผนที่ใช้ตอบว่างานถึงไหน ให้ตอบเทียบกับช่วงเหล่านี้ ไม่ตอบด้วยจำนวน commit หรือจำนวนเทสต์

### M0 วางฐาน (ทั้งสองคน)

ส่งมอบ:

- โปรเจกต์ที่สร้างจาก RR stack อยู่ใน repo นี้ โดย `bun run check`, `smoke` และ `e2e` ผ่านทั้งในเครื่องและใน CI
- สัญญาของ sync client พร้อมตัวที่ทำงานในหน่วยความจำ และหน้ารายการ issue หน้าแรกที่ใช้สัญญานั้น
- หน้าตาที่เจ้าของเลือกจาก mockup และ token ของธีม
- รายงานการทดลอง host ซึ่งต้องมี
  - การ deploy แอปของแม่แบบขึ้น Vercel กับ Neon แผนฟรี โดย server กับฐานข้อมูลอยู่ภูมิภาคเดียวกัน
  - การเปิดแท็บค้าง 24 ชั่วโมงด้วยโค้ดการเชื่อมต่อแบบที่ Lamdap จะใช้ ทั้งแบบเปิดและปิดการสะกิด แล้วอ่านเวลาที่ถูกคิดจาก dashboard ของ Vercel และ Neon
  - เวลาตอบของ request แรกหลังหลับ และเวลาของการเขียนหนึ่งครั้งที่มีการล็อก
  - พื้นที่และจำนวนการเชื่อมต่อฐานข้อมูลที่แผนฟรีให้
  - การ deploy แบบเดียวกันบนเครื่องของตัวเองด้วย compose กับ Caddy ของแม่แบบ

ถือว่าเสร็จเมื่อ:

- เปิด PR แล้ว CI ผ่าน และมีลิงก์ที่เปิดได้จริง
- ทั้งสองคนรัน `bun run dev` ในเครื่องของตัวเองได้
- เจ้าของตัดสินที่ host ของระบบจริงแล้ว โดยมีรายงานการทดลองประกอบ

### M1 Engine กับ server ครบ และใช้งานจริงได้

M1 มีสามด่าน ตรวจผ่านทีละด่าน

**M1.1 แกนของ protocol**

- ส่งมอบ: ตาราง, ทางลงบันทึก, push, pull, bootstrap, poke, กติกาทั้งหมดในข้อ 7 และ 8.4, การตรวจตำแหน่ง, เวอร์ชัน, sync client แบบเก็บในหน่วยความจำ, ตัวจำลอง
- ถือว่าเสร็จเมื่อ: เทสต์ของ server ในข้อ 14 ผ่านครบ, `bun run sim` ผ่านเกณฑ์ขั้นต่ำ และมีเอกสารอธิบาย engine ฉบับสั้นที่เจ้าของตรวจและแก้เองแล้ว

**M1.2 การเข้าถึง**

- ส่งมอบ: ระบบปิด, รหัสเชิญ, เจ้าของระบบคนแรก, สมาชิกภาพ, การตั้งรหัสผ่านใหม่, การตรวจของ WebSocket และของคำขอที่เปลี่ยนข้อมูล, ชนิดของระบบ, `smoke` กับงานของ CI ที่เขียนใหม่, การถอดหน้าตัวอย่างและโมดูล todo ของแม่แบบ
- ถือว่าเสร็จเมื่อ: ทุกหัวข้อในข้อ 10 มีเทสต์หรือหลักฐานการตั้งค่า และผู้ที่ไม่ใช่ผู้เขียนตรวจรายการนั้นครบแล้ว

**M1.3 ใช้งานจริง**

- ส่งมอบฝั่งหน้าจอ: โครงของแอป, รายการ issue, สร้างและแก้ issue (หัวข้อ, รายละเอียดพร้อมหน้าจอแก้ชนกัน, สถานะ, ความสำคัญ, ผู้รับผิดชอบ), ตัวบอกสถานะ, รายการที่ไม่สำเร็จ, คำเตือนก่อนออกจากหน้าเมื่อมีรายการค้าง
- ส่งมอบฝั่งระบบ: deployment ของระบบจริงบนที่ host ที่เจ้าของเลือก, การสำรองตามรอบ, ขั้นตอนกู้คืน, การส่งออก
- ถือว่าเสร็จเมื่อ
  - เทสต์ end-to-end ที่เปิดสองเบราว์เซอร์กับระบบที่ deploy แล้วและไม่ได้หลับ ยืนยันว่าการแก้ของฝั่งหนึ่งปรากฏที่อีกฝั่งภายใน 1 วินาทีเมื่อเปิดการสะกิด หรือภายในหนึ่งรอบการดึงบวก 1 วินาทีเมื่อปิด
  - reload แล้วข้อมูลยังอยู่
  - ซ้อมกู้คืนฐานข้อมูลตามข้อ 9.4 สำเร็จหนึ่งครั้ง คือหลังกู้คืน เครื่องที่เปิดค้างอยู่โหลดใหม่เอง รายการที่ค้างในคิวไปถึง server และไม่มีคิวค้าง

### M2 หน้าจอครบ (งานหน้าจอล้วน)

ส่งมอบ: project, label, board, ตัวกรองและค้นหา, command palette และคีย์ลัด, ถังขยะ, ตั้งค่า

ถือว่าเสร็จเมื่อ: ทุกอย่างในขอบเขตรุ่นแรกทำได้โดยไม่ใช้เมาส์ รวมถึงตอนแป้นเป็นภาษาไทย และเทสต์ end-to-end กับการตรวจการเข้าถึงผ่าน

### M3 Offline (งาน engine ล้วน)

ส่งมอบ: ข้อ 8.6 ถึง 8.10 ส่วนที่เป็นของ M3 ทั้งหมด และตัวจำลองที่มีความผิดปกติของ M3

ถือว่าเสร็จเมื่อฉากนี้ผ่านในเทสต์ end-to-end:

1. ปิดเน็ต แล้วเปิดแอปได้
2. สร้างและแก้ issue รวมถึงบันทึกรายละเอียดของ issue เดียวกันสองครั้ง
3. ปิดแท็บ แล้วเปิดแท็บใหม่ขณะยังไม่มีเน็ต
4. เห็นการแก้ไขทั้งหมดจากข้อ 2
5. ต่อเน็ต แล้วทุกอย่างไปถึง server ครบ ไม่ซ้ำ และไม่มีรายการใดถูกปฏิเสธ

และ: รายการที่ไม่สำเร็จยังอยู่หลังปิดแล้วเปิด, ตัวจำลองผ่านเกณฑ์ขั้นต่ำ, เอกสารอธิบาย engine อัปเดตส่วน offline แล้ว

### M4 พร้อมใส่ portfolio (ทั้งสองคน)

ส่งมอบ: deployment ของเดโมตามข้อ 12 พร้อมงานล้างประจำวัน, README และบทความอธิบาย engine และการสร้างบน RR stack, วิดีโอสั้น, การตรวจการเข้าถึงและความเร็วที่ 10,000 issue

ถือว่าเสร็จเมื่อ: คนแปลกหน้าที่ได้ลิงก์ลองเดโมได้ภายใน 10 วินาทีโดยไม่สมัคร, เดโมเข้าถึงข้อมูลจริงไม่ได้ และ README อธิบาย engine พร้อมผลทดสอบ

### ลำดับ

M0 → M1.1 → M1.2 → M1.3 → (M2 กับ M3 ขนานกัน) → M4 งานหน้าจอของ M1.3 เริ่มได้ตั้งแต่จบ M0 เพราะใช้สัญญาของ sync client ที่ M0 ส่งมอบ

ตัวเลือกแรกหลังรุ่นแรก: comment, undo, ช่องทางสำหรับ AI agent, หลายแท็บที่ทำงานสดพร้อมกัน, การกู้คืนทีละ workspace, เดโมที่รันในเบราว์เซอร์ล้วนด้วยการ compile แกน server เป็น WebAssembly

## 16. ความเสี่ยง

| ความเสี่ยง | การรับมือ |
|---|---|
| บั๊กของ engine ทำให้ข้อมูลเพี้ยนหรือหาย | เทสต์ของ server, ตัวจำลองกับ I1 ถึง I7, server เป็นตัวจริง, การตรวจตำแหน่ง, ปุ่มล้างสำเนา, รายการที่ไม่สำเร็จ |
| คิวของเครื่องค้างถาวร | กติกาว่าเลขทุกเลขต้องไปถึง server, mutation ว่าง, การจับ panic เป็นราย mutation, การแยกความล้มเหลวชั่วคราวออกจากความผิดพลาดของโค้ด, I7 |
| โควตาฟรีของ Vercel หมด แล้วทุกโปรเจกต์ในทีมเดียวกันหยุด | ไม่เปิด WebSocket ค้างบน Vercel แผนฟรี, เดโมอยู่คนละทีม, ปิดการเชื่อมต่อเมื่อแท็บถูกซ่อน, วัดจริง 24 ชั่วโมงใน M0 |
| ที่ host แผนฟรีไม่เสถียร: container หลับ, รุ่น beta, เพดานเวลาของ Neon | การออกแบบไม่พึ่งการสะกิด, ทางเลือกเป็นเครื่องของตัวเอง, เจ้าของตัดสินใน M0 |
| การกู้คืนฐานข้อมูลทำให้เครื่องใช้ข้อมูลเพี้ยนหรือคิวค้าง | การตรวจตำแหน่งทุก request, ขั้นตอนในข้อ 8.10, ความผิดปกตินี้อยู่ในตัวจำลอง, ซ้อมจริงก่อนปิด M1 |
| migration ทำข้อมูลจริงเสีย | สำรองก่อน deploy, migration แบบเพิ่มเท่านั้นภายในหนึ่งรุ่น, การแก้ข้อมูลต้องลงบันทึก |
| ระบบปิดทำให้เครื่องมือของแม่แบบใช้ไม่ได้ | เขียน `smoke` กับงานของ CI ใหม่ใน M1.2, เทสต์สมัครผ่านทางปกติ |
| Rust ทำให้ทำงานช้าลง เพราะเวลา compile และขั้นตอนของ sqlx | แนวทางของ stack มีคำสั่งเดียวที่บอกว่าเสร็จ, M1 แบ่งเป็นสามด่าน |
| ตัวจำลองที่คุยกับ server จริงช้า | ส่ง request ตามลำดับเพื่อให้รันซ้ำได้, มีรอบยาวแยกจาก CI ของ PR |
| แอปที่เป็น local-first ใช้ส่วนของแม่แบบได้ไม่เต็ม จนชู stack ได้ไม่ชัด | ใช้สัญญา, การสร้าง client, login, เทสต์ และ deploy ของ stack เต็มที่ และเขียนในบทความว่าส่วนไหนใช้ ส่วนไหนเพิ่ม |
| ขอบเขตบวม เพราะ Linear มีฟีเจอร์มาก | รายการสิ่งที่ไม่ทำในข้อ 3 และ milestone ในข้อ 15 |
| สองคนแก้ชนกัน | ขอบเขตตามโฟลเดอร์, สัญญาสองชั้น, M2 กับ M3 ไม่แตะไฟล์ชุดเดียวกัน |
| service worker ทำให้ผู้ใช้ค้างอยู่ที่แอปรุ่นเก่า | กติกาในข้อ 8.9 และ 8.10 และเทสต์ end-to-end ของการเปลี่ยนเวอร์ชัน |
| สิทธิ์ในโค้ดของสองคนไม่ชัด ทั้งที่ license สงวนสิทธิ์เชิงพาณิชย์ | สองคนตกลงเรื่องความเป็นเจ้าของเป็นลายลักษณ์อักษรก่อน jxyluvcode เริ่มเขียนโค้ด |

## 17. สิ่งที่ปล่อยให้ผู้สร้างตัดสิน

- รูปร่างของ type ใน Rust, ชื่อเส้นทาง, ชื่อ `operation_id`, โครงตารางและ index
- รหัส error ที่เพิ่มจากของแม่แบบ และรูปแบบของเหตุผลการปฏิเสธ
- วิธีอ่านเนื้อหาของ op แบบผ่อนปรนโดยที่สัญญายังระบุ type ครบ
- วิธีจับ panic เป็นราย mutation และวิธีกันไม่ให้ push ที่รอล็อกแย่งการเชื่อมต่อของ pull
- เวลาที่ยอมให้รอล็อก และงบเวลาของ request
- Library ฝั่งเว็บ: markdown, ลากวาง, ตัวห่อ IndexedDB, fractional index, service worker
- โครง IndexedDB และรูปแบบของ URL ของ issue ภายใต้เงื่อนไขว่าเปิดด้วย id ได้เสมอ
- ขนาดหน้า, เพดานอัตรา, รอบเวลาของ pull และสัญญาณชีพ
- ที่อยู่ของตัวจำลอง วิธีที่มันเริ่ม หยุด และกู้คืนฐานข้อมูลของ server ทดสอบ และระบบปฏิบัติการที่ CI รันมัน
- รายการคีย์ลัดทั้งหมด
- ค่าเพดานของเดโม
