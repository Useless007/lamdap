# เอกสารออกแบบ: issue tracker แบบ local-first พร้อม sync engine ที่เขียนเอง

- วันที่: 26 พ.ย. 2569 (2026-11-26)
- สถานะ: เจ้าของอนุมัติแล้วเมื่อ 26 พ.ย. 2569 (ฉบับแก้หลังการทบทวนครั้งที่ 1)
- ผู้ทำ: Useless007 (เจ้าของ ดูแล engine กับ server) และ jxyluvcode (ดูแลหน้าเว็บ และร่วมใช้งาน)
- ชื่อโปรเจกต์: **Lamdap** (ลำดับ)

> **กำลังแก้ไข:** เมื่อ 26 พ.ย. 2569 เจ้าของตัดสินให้สร้าง Lamdap บน [RR stack](https://github.com/Useless007/rr-stack) (React Router + Rust/Axum + Postgres) แทน Cloudflare Workers และเปลี่ยน license เป็น PolyForm Noncommercial 1.0.0 เนื้อหาเรื่อง server, การ host, เดโม และ milestone ในเอกสารนี้ยังเป็นฉบับเดิม และจะถูกแก้ในฉบับถัดไป ส่วนหลักการของ sync engine ในข้อ 8 ยังใช้ตามเดิม

ป้ายที่ใช้ทั้งเอกสาร:

- **[เจ้าของ]** สิ่งที่เจ้าของพูดหรือเลือกเอง
- **[ข้อเสนอ]** ค่าเริ่มต้นที่เสนอในการออกแบบ เจ้าของค้านได้
- **[ผู้สร้าง]** สิ่งที่ปล่อยให้คนลงมือสร้างตัดสิน

## 1. สรุปสำหรับอนุมัติ

### 1.1 จะได้อะไร

- เว็บแอปติดตามงานสำหรับทีมเล็ก ใช้คีย์บอร์ดเป็นหลัก แก้แล้วเห็นผลทันที เห็นการแก้ของอีกคนสด และใช้ต่อได้ตอนไม่มีเน็ต
- Sync engine ที่เขียนเอง ตามหลักเดียวกับที่ Linear ใช้ พร้อมชุดทดสอบจำลองที่เป็นหลักฐานว่าข้อมูลไม่เพี้ยนและไม่หาย
- Repo สาธารณะบน GitHub เดโมที่คนนอกลองได้โดยไม่ต้องสมัคร และบทความอธิบายว่า engine ทำงานอย่างไร
- แบ่งเป็น 5 ช่วง: M0 วางฐาน, M1 engine กับ server ครบและใช้งานจริงได้, M2 หน้าจอครบ, M3 ทำงานตอน offline, M4 พร้อมใส่ portfolio (รายละเอียดข้อ 15)

### 1.3 ค่าเริ่มต้นที่เสนอ (ค้านได้)

- **Stack** TypeScript ทั้งหมด หน้าเว็บ React + Vite + Tailwind + Base UI ส่วน server ใช้ Cloudflare Workers + Durable Objects + D1 บนแผนฟรี
- **ระบบปิด** login ผ่าน GitHub ได้เฉพาะบัญชีที่เจ้าของ workspace เชิญด้วยชื่อ GitHub
- **เดโม** รันในเบราว์เซอร์ทั้งหมด ไม่เรียก server จึงไม่กินโควตาและแตะข้อมูลจริงไม่ได้
- **Offline** รวมถึงการเปิดแอปขณะไม่มีเน็ต
- **หลายแท็บ** ตั้งแต่ M3 มีแท็บเดียวต่อเบราว์เซอร์ที่ทำงาน sync คือแท็บที่กำลังใช้อยู่ แท็บอื่นหยุดชั่วคราวและกลับมาทำงานเมื่อถูกเลือก
- **รายละเอียดของ issue** บันทึกเมื่อกดบันทึกหรือออกจากช่อง server ไม่รับการบันทึกที่จะทับข้อความซึ่งผู้บันทึกยังไม่เคยเห็น ผู้บันทึกจะเห็นทั้งสองฉบับแล้วเลือกเอง ยังไม่มีการพิมพ์พร้อมกันในข้อความเดียวกัน
- **ข้อมูลใน workspace จริงถือว่าถาวรตั้งแต่ M1** จึงต้องมีการย้าย schema และวิธีกู้คืนตั้งแต่ M1
- **การลบ** คือย้ายลงถังขยะและกู้คืนได้ รุ่นแรกไม่มีการลบถาวร
- สถานะงานมี 5 ค่าตายตัว ความสำคัญมี 5 ค่าตายตัว
- รุ่นแรกยังไม่มี comment, undo และการแจ้งเตือน
- ออกแบบให้ลื่นที่ 10,000 issue และ 20 สมาชิกต่อ workspace
- ตัวหนังสือบนปุ่มและเมนูเป็นภาษาอังกฤษ เนื้อหาพิมพ์ไทยได้เต็มรูปแบบ วันที่แสดงตามภาษาของเบราว์เซอร์ (เครื่องไทยเห็นปี พ.ศ.)
- README เป็นภาษาอังกฤษ ภาษาของบทความตัดสินตอนเริ่ม M4
- ไม่มีกำหนดส่ง ทำตามลำดับ M0 ถึง M4

## 2. ที่มาและเหตุผล

- **[เจ้าของ]** อยากได้เครื่องมือติดตามงานที่ปรับแต่งเป็นของตัวเอง และอยากมีผลงานติดตัวไว้ใส่ portfolio
- ตั้งต้นจาก repo `linear/linear` แต่ตรวจแล้วพบว่าเป็น SDK ไม่ใช่ตัวแอป ตัวแอป Linear เป็น closed source จึงไม่มีอะไรให้ fork
- **[เจ้าของ]** เลือกสร้าง issue tracker ของตัวเองแนวเดียวกับ Linear
- **[เจ้าของ]** เพื่อน (jxyluvcode) เข้ามาทั้งเขียนโค้ดด้วยกันและใช้ tracker ด้วยกัน
- **[เจ้าของ]** เลือกเขียน sync engine เอง เพื่อให้เป็นผลงานที่แสดงฝีมือทางวิศวกรรมใน portfolio ได้เต็มที่

สิ่งที่เจ้าของยังไม่ได้บอก และเอกสารนี้ตั้งสมมติฐานแทน:

- ตอนนี้ใช้เครื่องมืออะไรติดตามงาน และขัดใจตรงไหน: ไม่ทราบ จึงยึดขอบเขตรุ่นแรกที่เสนอไปและเจ้าของไม่ได้ค้าน
- Portfolio จะให้ใครดู: สมมติว่าเป็นคนสายเทคนิค จึงเน้นหลักฐานทางวิศวกรรมและเดโมที่ลองได้ทันที
- กำหนดเวลาและเวลาที่แต่ละคนมีต่อสัปดาห์: ไม่ทราบ จึงถือว่าไม่มีกำหนดส่ง ถ้ามี ต้องจัดลำดับใหม่ก่อนเขียนแผนงาน

## 3. เป้าหมาย สิ่งที่ไม่ทำ และสิ่งที่ถือว่าล้มเหลว

### เป้าหมาย

- **G1** เจ้าของกับเพื่อนใช้ติดตามงานจริงทุกวัน
- **G2** อ้างใน portfolio ได้ว่า "เขียน sync engine เอง และพิสูจน์ได้ว่าถูกต้อง" มี repo, เดโม และบทความรองรับ
- **G3** สองคนทำงานขนานกันได้โดยไม่ชนกัน

### ไม่ทำในรุ่นแรก

- Comment, undo/redo, การแจ้งเตือน, ประวัติการแก้ไขที่ดูได้ในหน้าจอ
- Cycle, roadmap, สถานะงานที่ตั้งเอง, ทีมย่อยหรือสิทธิ์ที่ละเอียดกว่า owner กับ member
- การพิมพ์พร้อมกันในข้อความเดียวกัน, การแสดงว่าใครกำลังดูอะไรอยู่
- หลายแท็บที่ทำงานสดพร้อมกันหลัง M3 (ดูข้อ 8.8)
- แอปมือถือ, การเชื่อมกับบริการอื่น, ไฟล์แนบและรูปภาพ, อีเมล
- ช่องทางให้ AI agent เปิดและอัปเดต issue (เก็บไว้เป็นรุ่นสอง เพราะเป็นจุดต่างจาก Linear)
- การโหลดข้อมูลบางส่วน (partial sync) สำหรับ workspace ที่ใหญ่กว่าเพดานในข้อ 4
- การนำเข้าข้อมูลจากเครื่องมืออื่น, การลบถาวรโดยผู้ใช้, หลายภาษาใน UI

### ถือว่าล้มเหลว แม้ใช้งานได้

- **A1** หน้าตาหรือชื่อเหมือน Linear จนดูเป็นของลอก
- **A2** ข้อมูลที่ผู้ใช้พิมพ์หายไปเงียบ ๆ
- **A3** Engine ทำงานได้ในเดโม แต่ไม่มีหลักฐานว่าถูกต้อง และผู้ทำอธิบายไม่ได้ว่ามันทำงานอย่างไร
- **A4** เดโมสาธารณะทำให้ workspace จริงใช้งานไม่ได้ หรือเข้าถึงข้อมูลจริงได้
- **A5** สองคนแก้ไฟล์ชนกันเป็นประจำ

## 4. ข้อจำกัด

### งบประมาณ: 0 บาทต่อเดือน บนแผนฟรีของ Cloudflare **[ข้อเสนอ]**

| ส่วน | เพดานแผนฟรี |
|---|---|
| Worker | 100,000 request ต่อวัน, CPU 10 ms ต่อ request, หน่วยความจำ 128 MB |
| ไฟล์หน้าเว็บ (static assets) | ฟรีและไม่จำกัด ไม่นับเป็น request ของ Worker |
| Durable Objects | ใช้ได้เฉพาะแบบ SQLite, 100,000 request ต่อวัน, 13,000 GB-s ต่อวัน, อ่าน 5 ล้านแถวต่อวัน, เขียน 100,000 แถวต่อวัน, เก็บรวม 5 GB |
| D1 | อ่าน 5 ล้านแถวต่อวัน, เขียน 100,000 แถวต่อวัน, เก็บรวม 5 GB |

- เกินเพดานรายวันแล้วคำสั่งประเภทนั้นจะ error จนถึง 00:00 UTC (07:00 เวลาไทย) และเพดานนับรวมทั้งบัญชี
- การเขียนหนึ่งแถวนับเพิ่มตามจำนวน index ของตาราง mutation หนึ่งชุดจึงเขียนราว 5 แถว การใช้งานจริงของสองคนอยู่ที่ไม่กี่เปอร์เซ็นต์ของโควตา
- WebSocket แบบ Hibernation ไม่คิดเวลาทำงานตอนไม่มีข้อความ
- เอกสาร Cloudflare ระบุว่า Durable Object มีเพดาน CPU ต่อครั้งเท่ากับ Worker จึงต้องถือว่า 10 ms ใช้กับ Durable Object ด้วย ผลคือทุก request ต้องเป็นงานก้อนเล็ก (ดูข้อ 9.3)
- เอกสาร Cloudflare ให้ตัวเลขพื้นที่ต่อ object บนแผนฟรีไม่ตรงกันสองแห่ง (1 GB กับ 10 GB) จึงออกแบบตาม 1 GB
- เรื่องที่เอกสารไม่ระบุ และต้องวัดจริงใน M0: ข้อความ WebSocket และ ping นับโควตา request อย่างไร, การกู้คืนย้อนเวลาใช้ได้บนแผนฟรีหรือไม่, CPU จริงของแต่ละงาน
- ทางออกถ้าเพดานไม่พอ: แผน Workers Paid เดือนละ 5 ดอลลาร์ ซึ่งเจ้าของต้องเป็นคนตัดสิน

### ขนาดที่ออกแบบรองรับ **[ข้อเสนอ]**

- ไม่เกิน 10,000 issue และ 20 สมาชิกต่อ workspace
- การกระทำในเครื่อง (เปิด issue, เปลี่ยนสถานะ, กรอง) แสดงผลภายใน 100 ms ที่ 10,000 issue
- การแก้ของอีกคนปรากฏภายใน 1 วินาทีบนเน็ตปกติ

### อื่น ๆ

- ผู้ใช้อยู่ในไทย Durable Object ต้องวางในภูมิภาคเอเชียแปซิฟิก
- รองรับ Chrome, Edge, Firefox, Safari รุ่นปัจจุบันบน desktop หน้าจอมือถือเปิดได้แต่ไม่ได้ปรับให้เหมาะ
- Repo คือ `Useless007/lamdap` เป็น public ตั้งแต่วันแรก มี `jxyluvcode` เป็น collaborator แต่ละคน commit ด้วยตัวตน git ของตัวเอง
- เพราะ repo เป็น public ทุกอย่างที่ commit ต้องเปิดเผยได้: ไม่มี secret ไม่มีข้อมูลของงานอื่น และไม่มีข้อมูลส่วนตัว
- ห้ามใช้ชื่อ โลโก้ หรือหน้าตาของ Linear และไม่ใช้โค้ดจาก `linear/linear`
- เครื่องมือที่ต้องมีในเครื่อง: Node 22, pnpm และ `wrangler`
- สิ่งที่เจ้าของต้องทำเอง เพราะเป็นการสร้าง secret หรือ login แบบโต้ตอบ: สมัครและ login Cloudflare, สร้าง GitHub OAuth App แล้วใส่ secret

## 5. แนวทางที่พิจารณา

| | 1. เขียน sync engine เองแบบ Linear | 2. ใช้ Electric + TanStack DB | 3. API ธรรมดา + ดันข้อมูลสด |
|---|---|---|---|
| ทำงานยังไง | แต่ละเครื่องเก็บสำเนา แก้แล้วเห็นทันที server จัดลำดับและกระจาย | library sync ฝั่งอ่านให้ เขียนฝั่งบันทึกเอง | ทุกการแก้ไขไป server ก่อน |
| Offline | ได้ | ได้ | ไม่ได้ |
| ข้อแลก | งานมากสุด | ดูแล 3 ชิ้น, TanStack DB ยังเป็น RC, ผลลัพธ์คล้ายเดโม Linearlite ของ Electric เอง | ไม่มีจุดขาย |

ตัดออก: Zero (เอกสารทางการระบุว่าไม่รองรับการแก้ไขตอน offline) และ CRDT (จัดการสิทธิ์รายคนยาก และ Linear ไม่ได้ใช้กับ issue)

**[เจ้าของ] เลือกแนวทาง 1** เพื่อให้เป็นผลงานที่แสดงฝีมือทางวิศวกรรมได้เต็มที่

Stack ที่พิจารณาสำหรับ server:

- **TypeScript บน Cloudflare Durable Objects [ข้อเสนอที่เลือก]** schema มีที่เดียว จำลองหลายเครื่องในเทสต์ได้ Durable Object ทำงานทีละคำสั่งจึงได้ลำดับที่แน่นอนโดยไม่ต้องล็อก และไม่ต้องเปิดเครื่องของเจ้าของให้คนนอก
- Go + Postgres: เป็น stack ที่เจ้าของใช้ในงานอื่น แต่ต้องเขียน schema สองภาษา ทดสอบการ sync ข้ามภาษายากกว่า และต้องหาที่ host

เจ้าของเห็นข้อเสนอนี้แล้วและไม่ได้ค้าน

## 6. ภาพรวมสถาปัตยกรรม

```

          │
          ▼  HTTPS และ WebSocket
Cloudflare Worker: เสิร์ฟหน้าเว็บ, login, ตรวจสิทธิ์, ส่งต่อ
 ├─ D1: ผู้ใช้, session, รายชื่อผู้ได้รับเชิญ, สารบัญ workspace
 └─ WorkspaceDO: หนึ่งตัวต่อ workspace (SQLite)
      ├─ ตารางข้อมูลงาน และรายชื่อสมาชิกของ workspace
      ├─ บันทึกความเปลี่ยนแปลง เรียงตาม syncId พร้อมที่มาของแต่ละรายการ
      └─ ตาราง client และผลการปฏิเสธ
```

หลักที่ทั้งระบบยึด:

1. **Server เป็นตัวจริงเสมอ** สำเนาในเครื่องล้างแล้วโหลดใหม่ได้ทุกเมื่อ
2. **Server เป็นผู้จัดลำดับ** ทุกการแก้ไขที่ถูกรับจะได้เลข `syncId` ที่เพิ่มขึ้นทีละหนึ่งภายใน workspace
3. **UI ไม่รอ server** UI อ่านจาก view และเขียนผ่านคำสั่งแก้ไขเท่านั้น
4. **ส่งซ้ำได้โดยไม่เกิดผลซ้ำ** mutation เดียวกันส่งกี่ครั้งก็มีผลครั้งเดียว และเลขของ mutation ต้องไม่ถูกใช้ซ้ำกับเนื้อหาอื่น
5. **ไม่มีการแก้ไขใดหายเงียบ** ทุกคำสั่งจบด้วยการถูกรับ หรือถูกปฏิเสธพร้อมแจ้งผู้ใช้และเก็บเนื้อหาไว้ให้

## 7. ข้อมูล

ทุก workspace มีข้อมูลชุดนี้ และสมาชิกทุกคนเห็นทั้งหมด

| Model | ฟิลด์หลัก |
|---|---|
| Workspace | ชื่อ, key สำหรับเลข issue (เช่น `LMD`) |
| Member | userId, ชื่อที่แสดง, รูป, บทบาท (owner หรือ member), removed |
| Project | ชื่อ, คำอธิบาย, สี, sortKey, deletedAt |
| Label | ชื่อ, สี, deletedAt |
| Issue | number, หัวข้อ, รายละเอียด (markdown), descriptionRev, สถานะ, ความสำคัญ, assigneeId, projectId, sortKey, createdBy, createdAt, updatedAt, deletedAt |
| IssueLabel | issueId, labelId, removed |

กติกาของข้อมูล **[ข้อเสนอ]**:

- **id** เครื่องสร้างเองเป็น UUID v7 จึงสร้างข้อมูลตอน offline ได้
- **number** ของ issue server เป็นผู้ออกตอนรับคำสั่ง issue ที่สร้างตอน offline แสดงเลขชั่วคราวจนกว่าจะ sync และต้องเปิดกับลิงก์ได้ด้วย id ตั้งแต่ก่อนมีเลข
- **ค่าที่ server เป็นผู้กำหนด** คือ number, createdAt, updatedAt, deletedAt และ descriptionRev ไม่เชื่อนาฬิกาหรือค่าเหล่านี้จากเครื่อง
- **descriptionRev** คือ `syncId` ของการแก้รายละเอียดครั้งล่าสุด ใช้ตรวจว่าผู้บันทึกเห็นฉบับล่าสุดแล้วหรือยัง (ข้อ 8.4)
- **สถานะ** มี 5 ค่า: backlog, todo, in_progress, done, canceled
- **ความสำคัญ** มี 5 ค่า: none, urgent, high, medium, low
- **ลำดับในคอลัมน์** ใช้ sortKey แบบ fractional index เป็นข้อความ ถ้าสองรายการมี sortKey เท่ากัน ให้แสดงเรียงตาม id และเครื่องต้องออก sortKey ใหม่ให้รายการที่เท่ากันก่อนแทรกระหว่างกลาง
- **Label ของ issue** เก็บเป็นแถวเชื่อม ไม่เก็บเป็น array ใน issue เพราะสองคนติด label คนละอันพร้อมกันต้องไม่ทับกันหาย id ของแถวเชื่อมได้จาก issueId กับ labelId
- **การลบ** ของ issue, project, label คือการย้ายลงถังขยะ ผู้ใช้กู้คืนได้ รุ่นแรกผู้ใช้สั่งได้แค่สร้างกับแก้ไข จึงไม่มีกรณีแก้ไขชนกับการลบถาวร
- **ขนาด** หัวข้อไม่เกิน 500 ตัวอักษร รายละเอียดไม่เกิน 100 KB

## 8. Sync engine

### 8.1 คำศัพท์

- **Client** ตัวตนของผู้ส่งคำสั่ง มี `clientId` เป็นค่าสุ่ม ผูกกับผู้ใช้คนเดียวตลอดไป (ข้อ 8.6 บอกว่าสร้างเมื่อไร)
- **Mutation** คำสั่งแก้ไขหนึ่งชุด ระบุด้วย `clientId` กับ `mutationId` (นับ 1, 2, 3 ต่อ client) และมีรายการ op แบบสร้างหรือแก้ไข server รับทั้งชุดหรือไม่รับเลย
- **Delta** ผลของ mutation หนึ่งชุดที่ถูกรับ มี `syncId` หนึ่งค่า, รายการแถวที่เปลี่ยนพร้อมค่าใหม่ของแต่ละฟิลด์ และ **ที่มา** คือ `clientId` กับ `mutationId` ของ mutation ที่ทำให้เกิด (ว่างถ้า server เป็นผู้เริ่มเอง)
- **ผลของ mutation** มีสามแบบ
  - **รับแล้ว ที่ syncId S** ถูกบันทึกถาวร
  - **ปฏิเสธ พร้อมเหตุผล** ถูกบันทึกถาวร
  - **ยังไม่ได้บันทึก** ไม่มีอะไรถูกบันทึก mutation ยังค้างอยู่และจะส่งใหม่ภายหลัง ใช้เมื่อ server บันทึกไม่ได้ชั่วคราว เช่น โควตาเขียนหมด

### 8.2 ฝั่ง server

WorkspaceDO ทำงานทีละข้อความ ระหว่างประมวลผล mutation ห้ามรอ I/O อื่นนอกจากที่เก็บข้อมูลของตัวเอง เพราะการรอ I/O อื่นเปิดให้ข้อความถัดไปแทรกเข้ามาได้ การตรวจทุกอย่างจึงใช้ข้อมูลในตัว object เท่านั้น

เมื่อได้รับ mutation ให้ทำตามลำดับนี้ใน transaction เดียวของ SQLite:

1. **ตรวจเจ้าของ client** `clientId` ที่เคยใช้แล้วต้องเป็นของผู้ใช้คนเดิม ถ้าไม่ใช่ให้ปฏิเสธ
2. **ตรวจลำดับ** เทียบ `mutationId` กับค่าล่าสุดที่ประมวลผลแล้วของ client นั้น
   - เท่ากับค่าล่าสุดบวกหนึ่ง: ทำต่อ
   - น้อยกว่าหรือเท่ากับค่าล่าสุด และเนื้อหาตรงกับที่เคยได้รับ: ไม่ทำซ้ำ ตอบผลเดิม
   - น้อยกว่าหรือเท่ากับค่าล่าสุด แต่เนื้อหาไม่ตรง: เป็นข้อผิดพลาดร้ายแรงของเครื่อง ตอบ error ที่เครื่องต้องแสดงให้ผู้ใช้เห็น ห้ามตอบผลเดิม
   - มากกว่าค่าล่าสุดบวกหนึ่ง: มีช่องว่าง ตอบกลับว่ารอเลขไหนอยู่
3. **ตรวจสิทธิ์และตรวจข้อมูล** ตามกติกาในข้อ 8.4
4. **บันทึก** ลงตารางข้อมูล พร้อมค่าที่ server เป็นผู้กำหนด
5. **ลงบันทึก** เพิ่ม delta ด้วย `syncId` ถัดไป พร้อมที่มาและลายนิ้วมือของเนื้อหา แล้วปรับค่าล่าสุดของ client
6. **กระจาย** ส่ง delta ให้ทุก WebSocket ของ workspace รวมถึงผู้ส่ง

กรณีที่ไม่ได้จบด้วยการรับ:

- **ปฏิเสธในขั้น 3** ไม่บันทึกข้อมูล แต่ปรับค่าล่าสุดของ client และเก็บผลการปฏิเสธพร้อมเหตุผลและลายนิ้วมือ แล้วแจ้งผู้ส่ง
- **โค้ดฝั่ง server ล้มระหว่างประมวลผล** ให้ถือเป็นการปฏิเสธด้วยเหตุผล `server-error` และบันทึกใน transaction ใหม่ เพื่อไม่ให้ mutation เดียวขวางคิวทั้งหมด
- **บันทึกไม่ได้** เช่น โควตาหมดหรือพื้นที่เต็ม ไม่มีอะไรถูกบันทึก ผลคือ "ยังไม่ได้บันทึก"

ลายนิ้วมือของเนื้อหาต้องคำนวณได้ทันทีโดยไม่รอ ใช้ตรวจการใช้เลขซ้ำ ไม่ใช่เพื่อความปลอดภัย

การเปลี่ยนแปลงที่ server เป็นผู้เริ่มเอง เช่น มีสมาชิกเข้าใหม่ ก็ลงบันทึกและได้ `syncId` เช่นกัน

### 8.3 ฝั่ง client

mutation หนึ่งชุดผ่านสถานะตามลำดับ: สร้างในเครื่อง, เข้าคิว (ได้ `mutationId` แล้ว), ส่งแล้ว, รู้ผลแล้ว

- **เมื่อผู้ใช้แก้ไข** ต่อท้าย pending และคำนวณ view ใหม่ทันที จากนั้นออก `mutationId` และส่งเมื่อเชื่อมต่ออยู่ โดยส่งตามลำดับเลข
- **เมื่อได้รับ delta** ต้องเป็น `syncId` ถัดจาก `lastSyncId` พอดี จึงนำไปใช้กับ base ถ้าเลขซ้ำให้ข้าม ถ้าเลขข้ามให้ขอส่วนที่ขาดก่อน
- **เมื่อไรเอา mutation ออกจาก pending** มีสองกรณีเท่านั้น
  - ผลคือรับแล้วที่ S และ `lastSyncId` ของเครื่องถึง S แล้ว ซึ่งปกติคือจังหวะที่ delta ซึ่งมีที่มาเป็น mutation นั้นถูกนำไปใช้
  - ผลคือปฏิเสธ
- **เมื่อถูกปฏิเสธ** ย้าย mutation ไปยังรายการที่ไม่สำเร็จพร้อมเนื้อหาและเหตุผล view กลับไปเป็นค่าของ base ผู้ใช้เลือกส่งใหม่หรือทิ้ง ถ้าการสร้างถูกปฏิเสธ op ที่ค้างอยู่ซึ่งแตะแถวเดียวกันให้รวมเข้าเป็นร่างเดียว ไม่แสดงเป็นหลายรายการ
- **เมื่อผลคือยังไม่ได้บันทึก หรือการเชื่อมต่อหลุดก่อนรู้ผล** mutation ยังอยู่ใน pending ส่งใหม่ด้วยเลขเดิมโดยหน่วงเวลาเพิ่มขึ้น และบอกผู้ใช้ว่า server บันทึกไม่ได้ชั่วคราว
- **เมื่อ server ตอบว่ามีช่องว่าง** โหลดคิวจากที่เก็บในเครื่องใหม่ แล้วส่งตั้งแต่เลขที่ server รอ

view ของแต่ละแถวคือค่าใน base ที่ถูกทับด้วย op ของทุก mutation ใน pending ตามลำดับ นี่คือการ rebase: เมื่อ base เปลี่ยน ค่าที่ผู้ใช้เพิ่งแก้ยังแสดงอยู่ และเพราะ mutation ออกจาก pending ก็ต่อเมื่อผลของมันอยู่ใน base แล้ว ค่าที่แสดงจึงไม่ย้อนกลับไปเป็นค่าเก่าชั่วขณะ

### 8.4 กติกาการตรวจและเมื่อแก้ชนกัน

| กรณี | ผล |
|---|---|
| สองคนแก้ฟิลด์เดียวกันของแถวเดียวกัน | คนที่ถึง server ทีหลังชนะ |
| สองคนแก้คนละฟิลด์ของแถวเดียวกัน | ได้ทั้งสองอย่าง |
| คนหนึ่งแก้ อีกคนย้ายลงถังขยะ | ได้ทั้งสองอย่าง แถวอยู่ในถังขยะพร้อมค่าที่แก้ |
| อ้างถึงสิ่งที่อยู่ในถังขยะ เช่น ย้าย issue เข้า project ที่ถูกย้ายลงถังขยะ | รับ สิ่งที่อยู่ในถังขยะถือว่ายังมีอยู่ |
| อ้างถึงสิ่งที่ไม่เคยมี | ปฏิเสธ |
| มอบงานให้สมาชิกที่ถูกถอดแล้ว | ปฏิเสธ งานเดิมของคนนั้นยังคงชื่อไว้ |
| สร้างแถวด้วย id ที่มีอยู่แล้ว | ปฏิเสธ ยกเว้น IssueLabel |
| ติด label ที่ติดอยู่แล้ว หรือสองคนติด label เดียวกัน | รับ และมีแถวเชื่อมแถวเดียว |
| สองคนติด label คนละอันให้ issue เดียวกัน | ได้ทั้งสองอัน |
| คนหนึ่งติด อีกคนถอด label เดียวกัน | คนที่ถึง server ทีหลังชนะ |
| แก้รายละเอียดของ issue โดยอิงฉบับที่ไม่ใช่ล่าสุด | ปฏิเสธ (ดูด้านล่าง) |

รายละเอียดของ issue **[ข้อเสนอ]**:

- บันทึกเมื่อผู้ใช้กดบันทึกหรือออกจากช่อง ไม่บันทึกทุกตัวอักษร และเป็น mutation ของตัวเองเสมอ ไม่รวมกับการแก้ฟิลด์อื่น
- คำสั่งแก้รายละเอียดต้องบอก `descriptionRev` ของฉบับที่ผู้ใช้เริ่มแก้ ถ้าไม่ตรงกับค่าปัจจุบัน server ปฏิเสธ
- เมื่อถูกปฏิเสธด้วยเหตุนี้ เครื่องแสดงข้อความของผู้ใช้คู่กับฉบับล่าสุด ให้ผู้ใช้รวมเองแล้วบันทึกใหม่ จึงไม่มีข้อความของใครถูกทับโดยที่ผู้ทับไม่เคยเห็น
- กติกานี้ครอบคลุมกรณีที่บันทึกตอน offline แล้วมาส่งทีหลังด้วย
- หัวข้อของ issue ใช้กติกาปกติ คือคนที่ถึงทีหลังชนะ
- ยกระดับได้ภายหลังด้วย CRDT เฉพาะฟิลด์นี้

### 8.5 การโหลดครั้งแรกและการเชื่อมต่อใหม่

**โหลดครั้งแรก (bootstrap)**

- ขอข้อมูลทีละหน้า หน้าแรกบอก `syncId` ณ ตอนเริ่ม
- การแบ่งหน้าต้องไล่ตาม primary key ที่ไม่เปลี่ยน ห้ามใช้ลำดับที่หรือคอลัมน์ที่เปลี่ยนค่าได้ และจำกัดขนาดหน้าด้วยจำนวนไบต์ ไม่ใช่จำนวนแถว
- เมื่อได้ครบทุกหน้า เครื่องขอ delta ตั้งแต่ `syncId` ตอนเริ่มมาใช้ทับตามลำดับ วิธีนี้ถูกต้องแม้มีคนแก้ระหว่างโหลด เพราะ delta บรรจุค่าใหม่ของฟิลด์ ไม่ใช่ส่วนต่าง การใช้ซ้ำตามลำดับจึงให้ค่าสุดท้ายเท่าเดิม
- delta สดที่เข้ามาระหว่างนี้ให้พักไว้ แล้วใช้ต่อท้ายเมื่อไล่ทันแล้ว
- UI เริ่มใช้ข้อมูลได้เมื่อขั้นตอนทั้งหมดเสร็จเท่านั้น

**เชื่อมต่อใหม่**

1. เครื่องแจ้งเวอร์ชันของ protocol, `clientId`, `lastSyncId` และเลขของ mutation ที่ยังอยู่ใน pending
2. Server ตอบผลของ mutation ในรายการนั้นที่ประมวลผลไปแล้ว (รับแล้วที่ S หรือปฏิเสธ) และเลขถัดไปที่รออยู่
3. เครื่องขอ delta ที่ขาดทีละหน้า และพัก delta สดไว้จนไล่ทัน
4. เครื่องส่ง mutation ที่ยังไม่ถูกประมวลผลตามลำดับ
5. mutation ที่รู้แล้วว่าถูกรับ ยังอยู่ใน pending จนกว่า `lastSyncId` จะถึง S ตามกติกาในข้อ 8.3

ถ้าเครื่องตามไม่ทันเกินกว่าที่ server จะส่ง delta ย้อนหลังให้ ให้ bootstrap ใหม่โดยไม่แตะ pending

**อื่น ๆ**

- การเชื่อมต่อใหม่ด้วย `clientId` เดิม แทนที่การเชื่อมต่อเก่าของ client นั้น server ปิดอันเก่า
- ตรวจการเชื่อมต่อด้วยข้อความ ping ที่ Durable Object ตอบอัตโนมัติโดยไม่ต้องตื่น และเชื่อมต่อใหม่แบบหน่วงเวลาเพิ่มขึ้นพร้อมสุ่ม
- UI แสดงสถานะการเชื่อมต่อและจำนวนรายการที่รอส่งเสมอ

### 8.6 ตัวตนของ client และเลขของ mutation **[ข้อเสนอ]**

เลขของ mutation ต้องไม่ถูกใช้ซ้ำ ไม่ว่าแท็บจะถูก reload, ถูกทำสำเนา หรือเบราว์เซอร์ล้มกลางคัน

- **ก่อน M3 (ยังไม่มีที่เก็บในเครื่อง)** ทุกครั้งที่โหลดหน้า สร้าง `clientId` ใหม่ และนับ `mutationId` ในหน่วยความจำ แต่ละแท็บจึงเป็น client อิสระที่ทำงานสดพร้อมกันได้ pending หายเมื่อปิดหรือ reload จึงต้องเตือนก่อนออกจากหน้าเมื่อยังมีรายการค้าง
- **ตั้งแต่ M3** มี client ถาวรหนึ่งตัวต่อเบราว์เซอร์ ต่อ workspace ต่อผู้ใช้ `clientId` กับตัวนับเลขถัดไปเก็บใน IndexedDB
  - การออก `mutationId` กับการเขียน mutation ลง outbox ต้องอยู่ใน transaction เดียวของ IndexedDB
  - ส่ง mutation ได้ก็ต่อเมื่อ transaction นั้นสำเร็จแล้วเท่านั้น
  - ห้ามเก็บตัวตนของ client ในที่ที่เบราว์เซอร์ทำสำเนาให้แท็บอื่นได้ เช่น sessionStorage

### 8.7 การเก็บในเครื่อง (M3)

IndexedDB หนึ่งฐานต่อ workspace ต่อผู้ใช้ มีส่วนเหล่านี้: แถวของ base, ค่ากำกับ (`lastSyncId`, เวอร์ชันของ protocol, ตัวตนของ client และตัวนับ), outbox และรายการที่ไม่สำเร็จ

กติกาการเขียน ซึ่งต้องถูกต้องแม้มีสองแท็บเขียนในเวลาใกล้กัน:

- **นำ delta ไปใช้** ใน transaction เดียว: ตรวจว่า `syncId` ต่อจากค่าที่เก็บไว้พอดี ถ้าใช่ให้เขียนแถวและปรับ `lastSyncId` ถ้าค่าที่เก็บไว้ถึงแล้วให้ข้ามการเขียนแถว ถ้าค่าที่เก็บไว้ยังตามหลังเกินหนึ่ง ให้ยกเลิกแล้วเขียน delta ที่ขาดตามลำดับก่อน จากนั้นลบรายการใน outbox ที่ที่มาของ delta ระบุถึงเสมอ ไม่ว่ารอบนี้จะได้เขียนแถวหรือไม่
- **ถูกปฏิเสธ** ใน transaction เดียว: ย้ายรายการจาก outbox ไปยังรายการที่ไม่สำเร็จ รายการที่ไม่สำเร็จอยู่จนกว่าผู้ใช้จะส่งใหม่หรือทิ้ง
- **bootstrap** เขียนลงพื้นที่พักก่อน แล้วสลับเป็น base เมื่อครบและไล่ delta ทันแล้ว base ที่เขียนไม่ครบต้องไม่ถูกนำมาใช้
- เปิดแอปครั้งถัดไป แสดงข้อมูลจากเครื่องก่อน แล้วตามให้ทันด้วย delta
- การแก้ไขล่าสุดอาจหายได้ถ้าเบราว์เซอร์ถูกปิดในไม่กี่มิลลิวินาทีก่อนเขียนลง outbox เสร็จ ในกรณีนั้นยังไม่มีอะไรถูกส่ง ข้อมูลจึงไม่เพี้ยน ยอมรับข้อจำกัดนี้
- ทางหนีเมื่อสำเนาในเครื่องมีปัญหา: ปุ่มล้างสำเนาแล้วโหลดใหม่ โดยไม่แตะ outbox และรายการที่ไม่สำเร็จ

### 8.8 หลายแท็บ (M3) **[ข้อเสนอ]**

- ในเบราว์เซอร์หนึ่งมีแท็บเดียวที่เป็น **ตัวทำงาน** คือถือ WebSocket, ส่ง mutation และนำ delta ไปใช้ เลือกด้วย Web Locks
- แท็บที่ผู้ใช้กำลังใช้อยู่แย่งสิทธิ์มาเป็นตัวทำงานเสมอ แท็บที่เสียสิทธิ์ปิด WebSocket หยุดนำ delta ไปใช้ แสดงเครื่องหมายว่าหยุดชั่วคราว และรอคิวรับสิทธิ์คืนเมื่อแท็บตัวทำงานถูกปิด
- แท็บที่ได้สิทธิ์โหลด base, outbox และรายการที่ไม่สำเร็จจาก IndexedDB ใหม่ทั้งหมด แล้วเชื่อมต่อด้วย client ถาวรตัวเดิม การแก้ไขที่ค้างส่งจากแท็บก่อนหน้าจึงปรากฏในแท็บใหม่ทันที แม้ยังไม่มีเน็ต
- ทุกแท็บเขียน mutation ลง outbox ได้ทันทีโดยไม่ต้องรอได้สิทธิ์ เพราะการออกเลขอยู่ใน transaction ของ IndexedDB เมื่อเขียนแล้วต้องแจ้งแท็บอื่น ตัวทำงานจะโหลดรายการใหม่ไปส่ง
- แท็บที่เพิ่งเสียสิทธิ์อาจยังทำงานค้างอยู่ชั่วครู่ ความถูกต้องต้องไม่ขึ้นกับว่ามันหยุดทันที กติกาที่รองรับคือ การออกเลขใน transaction, การตรวจ `syncId` ก่อนเขียน base, การแทนที่การเชื่อมต่อเก่าที่ server และการไม่ทำซ้ำที่ server
- ข้อจำกัดที่ยอมรับ: หน้าต่างที่ไม่ได้ถูกเลือกจะไม่อัปเดตสด

### 8.9 เปิดแอปขณะไม่มีเน็ต (M3) **[ข้อเสนอ]**

- ใช้ service worker เก็บไฟล์ของแอปไว้ในเครื่อง แอปจึงเปิดได้และแสดงข้อมูลจากเครื่องโดยไม่มีเน็ต
- ข้อมูลในเครื่องแสดงได้โดยไม่ตรวจ session กับ server เหมือนแอป offline ทั่วไป การป้องกันอยู่ที่กติกาการล้างข้อมูลในข้อ 10
- เมื่อต้องเปลี่ยนเวอร์ชัน (ข้อ 8.10) ต้องอัปเดต service worker ให้เสร็จก่อนโหลดหน้าใหม่ ห้ามวนโหลดแอปรุ่นเก่าจากที่เก็บไว้ซ้ำ ๆ

### 8.10 การเปลี่ยนเวอร์ชัน

- ทุก WebSocket จำเวอร์ชันของ protocol ที่ใช้ตอนเชื่อมต่อ Durable Object ต้องไม่รับข้อความจาก และไม่ส่ง delta ให้การเชื่อมต่อที่เวอร์ชันไม่ตรงกับโค้ดปัจจุบัน ให้ปิดด้วยรหัสเฉพาะ เหตุผลคือการเชื่อมต่อแบบ Hibernation อยู่รอดข้ามการ deploy การตรวจตอนเชื่อมต่อใหม่อย่างเดียวจึงไม่พอ
- กติกานี้ต้องมีตั้งแต่ M1 เพราะแท็บที่เปิดค้างไว้เจอ deploy ใหม่ได้ตั้งแต่วันแรก
- เมื่อถูกปิดด้วยรหัสนั้น เครื่องโหลดแอปรุ่นใหม่ ทิ้ง base แล้ว bootstrap ใหม่
- แต่ละรายการใน outbox จำเวอร์ชันที่สร้าง เมื่อรูปแบบของ mutation เปลี่ยน แอปรุ่นใหม่ต้องมีตัวแปลงจากรุ่นก่อน รายการที่แปลงไม่ได้ให้ย้ายไปยังรายการที่ไม่สำเร็จ ห้ามทิ้งเงียบ

### 8.11 ทางลัดที่ตั้งใจ **[ข้อเสนอ]**

- ไม่ตัดบันทึกความเปลี่ยนแปลง และไม่ลบแถวในตาราง client ในรุ่นแรก ที่ขนาดนี้ข้อมูลโตช้า ต้องทบทวนเมื่อพื้นที่เข้าใกล้เพดานในข้อ 9.3
- สมาชิกทุกคนเห็นข้อมูลทั้ง workspace จึงไม่มีการแยกว่าใครได้รับ delta ไหน

## 9. Server บน Cloudflare

### 9.1 Worker

- เสิร์ฟหน้าเว็บจาก static assets และให้ทุกเส้นทางของแอปตกไปที่หน้าเดียว
- จัดการ login ด้วย GitHub, session และรายชื่อผู้ได้รับเชิญ โดยเก็บใน D1
- ตรวจ session ก่อนส่งต่อทุกคำขอไปยัง WorkspaceDO ตัวตนที่ WorkspaceDO เชื่อต้องมาจาก Worker เท่านั้น ผู้ใช้ปลอมแปลงเองไม่ได้
- ตรวจ Origin ของคำขอเปิด WebSocket
- เส้นทางที่ไม่ต้อง login มีเท่าที่จำเป็นสำหรับการ login เท่านั้น

### 9.2 WorkspaceDO

- หนึ่งตัวต่อ workspace เรียกด้วยชื่อที่ได้จาก id ของ workspace
- ใช้ SQLite ของ Durable Object และ WebSocket แบบ Hibernation
- ไม่เก็บสิ่งสำคัญไว้ในหน่วยความจำ เพราะหน่วยความจำถูกล้างเมื่อหลับ ข้อมูลของแต่ละการเชื่อมต่อ (userId, clientId, บทบาท, session และเวลาหมดอายุ, เวอร์ชันของ protocol) เก็บใน attachment ของ WebSocket ซึ่งจำกัด 16 KB
- ไม่ตั้ง timer ค้างไว้ เพราะทำให้ไม่หลับ
- **สมาชิกภาพ** รายชื่อสมาชิกในตัว object เป็นตัวตัดสินว่าใครอ่านและเขียน workspace นี้ได้ การถอดสมาชิกต้องเขียนที่ object ก่อน แล้วปิด WebSocket ของคนนั้นทันที จากนั้นจึงปรับสารบัญใน D1 และลองใหม่จนสำเร็จทั้งสองที่ การซิงก์รายชื่อจาก D1 ต้องไม่ทำให้คนที่ถูกถอดกลับเข้ามา
- **Session** ตรวจเวลาหมดอายุจาก attachment ทุกข้อความ เมื่อผู้ใช้ logout Worker สั่งให้ปิด WebSocket ของ session นั้น
- **constructor** ต้องเบา ตรวจเวอร์ชันของ schema เท่านั้น
- **การย้าย schema** ต้องเป็นการเพิ่มตารางหรือคอลัมน์ หรือแบ่งเป็นขั้นเล็กที่ทำต่อจากที่ค้างได้ ห้ามไล่แก้ทั้งตารางในครั้งเดียว

แกนของ server ทำงานกับที่เก็บข้อมูลผ่านช่องทางแคบชุดเดียว ซึ่งมีตัวจริงสองแบบ: SQLite ของ Durable Object และแบบหน่วยความจำที่ใช้ในตัวจำลองกับเดโม ทั้งสองแบบต้องผ่านชุดทดสอบเดียวกัน

### 9.3 งบ CPU และพื้นที่

- ทุก request และทุกข้อความ WebSocket ต้องทำงานที่มีขนาดจำกัด ไม่วนอ่านข้อมูลทั้ง workspace ในครั้งเดียว
- bootstrap และการส่ง delta ย้อนหลังแบ่งเป็นหน้าตามจำนวนไบต์ เครื่องเป็นฝ่ายขอหน้าถัดไป
- เพดานเริ่มต้นของ mutation คือ 50 op และ 256 KB **[ผู้สร้าง ปรับตามผลวัด]**
- จำกัดอัตราต่อการเชื่อมต่อ
- เมื่อฐานข้อมูลของ workspace เกิน 500 MB ให้ปฏิเสธการสร้างและการแก้รายละเอียด พร้อมแจ้งผู้ใช้ เพื่อไม่ให้ชนเพดาน 1 GB โดยไม่รู้ตัว
- ขนาดหน้าและเพดานทั้งหมดต้องกำหนดจากผลวัดใน M0 ให้ CPU ที่ p99 ไม่เกินครึ่งหนึ่งของเพดาน

### 9.4 ความคงทนของข้อมูลจริง **[ข้อเสนอ]**

- ข้อมูลใน workspace จริงถือว่าถาวรตั้งแต่ M1 ห้ามล้างเพื่อความสะดวกในการพัฒนา
- การย้าย schema มีเลขเวอร์ชันและมีเทสต์ตั้งแต่ M1
- **ส่งออกและกู้คืน** ส่งออกทั้ง workspace เป็นไฟล์ JSON จากข้อมูลในเครื่อง และกู้คืนไฟล์นั้นเข้า workspace เปล่าได้ผ่าน mutation ปกติ ต้องซ้อมกู้คืนจริงหนึ่งครั้งก่อนปิด M1
- **การกู้คืนย้อนเวลา** SQLite ของ Durable Object กู้คืนย้อนได้ 30 วันตามเอกสาร ถ้า M0 ยืนยันว่าใช้ได้บนแผนฟรี ให้เขียนขั้นตอนกู้คืนไว้เป็นตาข่ายชั้นที่สอง
- ก่อน deploy ที่เปลี่ยน schema ของ server ต้องส่งออกข้อมูลเก็บไว้ก่อน

## 10. ความปลอดภัยและข้อมูลส่วนบุคคล

- **Login** ใช้ GitHub OAuth พร้อมค่า `state` ขอสิทธิ์เท่าที่จำเป็นสำหรับอ่านโปรไฟล์ ไม่เก็บรหัสผ่าน
- **ระบบปิด [ข้อเสนอ]**
  - เจ้าของระบบกำหนดด้วย id ตัวเลขของ GitHub ในค่าตั้ง ไม่ใช้ชื่อบัญชี เพราะชื่อเปลี่ยนมือได้
  - เจ้าของ workspace เชิญด้วยชื่อ GitHub ระบบแปลงเป็น id ตัวเลขและแสดงโปรไฟล์ให้ยืนยันก่อนบันทึก ไม่มีลิงก์เชิญที่ใครถือก็ใช้ได้
  - สร้าง workspace ได้เฉพาะเจ้าของระบบ เชิญและถอดสมาชิกได้เฉพาะ owner ของ workspace
  - บัญชีที่ไม่ได้รับเชิญ login ไม่ได้ และระบบไม่เก็บข้อมูลของบัญชีนั้น
- **Session** เป็น cookie แบบ HttpOnly, Secure, SameSite=Lax
- **ไม่เชื่อเครื่องผู้ใช้** ทุก mutation ถูกตรวจสิทธิ์และตรวจข้อมูลที่ server และ `clientId` ผูกกับผู้ใช้คนเดียว คนอื่นส่งในนามไม่ได้
- **Markdown** แสดงผลโดยไม่อนุญาต HTML ดิบ และอนุญาตเฉพาะลิงก์ `http`, `https`, `mailto`
- **ข้อมูลในเครื่อง** แยกฐานตามผู้ใช้ เมื่อ logout ให้ล้างข้อมูลในเครื่องของผู้ใช้นั้น โดยเตือนก่อนถ้ายังมีรายการรอส่ง เมื่อ server แจ้งว่าหมดสิทธิ์เข้า workspace ให้ล้างเช่นกัน โดยแจ้งจำนวนรายการที่ยังไม่ได้ส่ง
- **ทางลัด login สำหรับพัฒนาและทดสอบ** ต้องเปิดไม่ได้บน production ไม่ว่าด้วยค่าตั้งใด
- **ข้อมูลส่วนบุคคล** เก็บเท่าที่ต้องใช้ คือ id ของ GitHub, ชื่อที่แสดง และ URL รูป ไม่เก็บอีเมล เพื่อให้ภาระตาม PDPA น้อยที่สุด
- **Secret** ไม่อยู่ใน repo ใช้ที่เก็บ secret ของ Cloudflare และไฟล์ในเครื่องที่ถูก ignore
- งานส่วนนี้ต้องผ่านการตรวจด้านความปลอดภัยก่อน merge

## 12. เดโมสาธารณะ **[ข้อเสนอ]**

เดโมรันในเบราว์เซอร์ของผู้เยี่ยมชมทั้งหมด ไม่มี request ไปยัง API ของ server

- หน้าเดโมสร้าง engine ฝั่ง client สองตัว ("คุณ" กับ "เพื่อนร่วมทีม") และแกนของ server หนึ่งตัวที่ใช้ที่เก็บแบบหน่วยความจำ เชื่อมกันด้วยสายส่งในหน่วยความจำ
- ผู้เยี่ยมชมเห็นสองฝั่งพร้อมกันในหน้าเดียว แก้ฝั่งหนึ่งแล้วเห็นอีกฝั่งเปลี่ยน
- แต่ละฝั่งมีสวิตช์ตัดเน็ตของตัวเอง จึงลองแก้ตอน offline, แก้ชนกัน และต่อกลับได้
- แผงแสดงการ sync ของแต่ละฝั่ง: `lastSyncId`, คิวที่รอส่ง, สถานะการเชื่อมต่อ และบันทึกล่าสุดของ server
- ข้อมูลตัวอย่างสร้างในเครื่อง โหลดหน้าใหม่แล้วเริ่มใหม่
- โค้ดที่รันคือ engine และแกนของ server ชุดเดียวกับระบบจริง ต่างกันเฉพาะที่เก็บข้อมูลและสายส่ง หน้าเดโมต้องบอกเรื่องนี้ตรง ๆ

เหตุผล: เดโมที่รันบน server ต้องใช้โควตาฟรีก้อนเดียวกับ workspace จริง ซึ่งโควตาเขียนวันละ 100,000 แถวรับไม่ไหว และต้องมีระบบแขก, การลบตามเวลา และเพดานอีกชุด การรันในเบราว์เซอร์ตัดทั้งหมดนี้ และแสดงการทำงานของ engine ได้ชัดกว่า

ชุดเดียวกันนี้ใช้เป็นเครื่องมือพัฒนาหน้าเว็บตั้งแต่ M0 เดโมจึงมีให้ดูตั้งแต่ต้นและโตตามฟีเจอร์

## 13. Repo และการทำงานสองคน

โครงสร้าง **[ข้อเสนอ]** เป็น monorepo ด้วย pnpm workspaces:

| ที่ | หน้าที่ | ผู้ดูแล |
|---|---|---|
| `packages/schema` | นิยาม model, ตัวตรวจข้อมูล และรูปแบบข้อความระหว่างเครื่องกับ server นี่คือสัญญากลาง | ร่วมกัน |
| `packages/sync` | แกนของ engine ทั้งฝั่ง client และฝั่ง server เป็น TypeScript ล้วน รันได้ทั้งในเบราว์เซอร์, Node และ Workers พร้อมตัวจำลองสำหรับทดสอบ | เจ้าของ |
| `apps/server` | Worker, WorkspaceDO และ D1 เป็นชั้นบางที่ห่อแกนฝั่ง server | เจ้าของ |
| `apps/web` | React SPA รวมหน้าเดโม | jxyluvcode |
| `docs/design` | เอกสารออกแบบ และแผนงานใน `docs/design/plans` | ร่วมกัน |

สัญญาระหว่าง UI กับ engine มี 4 อย่าง:

1. อ่านข้อมูลแบบติดตามการเปลี่ยนแปลง
2. ส่งคำสั่งแก้ไข
3. อ่านสถานะ: การเชื่อมต่อ, จำนวนที่รอส่ง, หยุดชั่วคราว, ต้องอัปเดตเวอร์ชัน
4. อ่านและจัดการรายการที่ไม่สำเร็จ รวมถึงข้อมูลสำหรับหน้าจอแก้รายละเอียดชนกัน

M0 ต้องส่งมอบสัญญานี้พร้อมตัวที่ทำงานได้ในหน่วยความจำ เพื่อให้งานหน้าเว็บเริ่มได้โดยไม่รอ engine ตัวจริง

วิธีทำงาน:

- `main` ถูกป้องกัน ทุกการเปลี่ยนแปลงเข้าผ่าน PR และ CI ต้องผ่าน
- การแก้ `packages/schema` ต้องให้ทั้งสองคนเห็นชอบ เพราะกระทบทั้งสองฝั่ง
- model และกติกาฝั่ง server ทั้งหมดของรุ่นแรกทำให้เสร็จใน M1 เพื่อให้ M2 เป็นงานหน้าเว็บล้วน และ M3 เป็นงาน engine ล้วน สองช่วงนี้จึงทำขนานกันได้โดยไม่แตะไฟล์ชุดเดียวกัน
- การ merge เข้า `main` และการ deploy ต้องให้เจ้าของสั่ง

## 14. การทดสอบ: หลักฐานว่า engine ถูกต้อง

### ตัวจำลอง

รันหลาย client กับ server ในกระบวนการเดียว ด้วยตัวสุ่มที่กำหนด seed ได้ ที่เก็บในเครื่องและสายส่งเป็นตัวจำลองที่ควบคุมได้ การกระทำของผู้ใช้แต่ละครั้งที่ตัวจำลองสร้างมีรหัสซ่อนของตัวเอง เพื่อใช้ตรวจว่าสิ่งที่ server รับตรงกับสิ่งที่เครื่องบอกผู้ใช้

ความผิดปกติที่ต้องสุ่มใส่:

- การหน่วง, การตัดการเชื่อมต่อ, การส่งซ้ำ, ช่วง offline
- bootstrap ระหว่างมีคนแก้
- Durable Object หลับแล้วตื่น: ล้างหน่วยความจำของ server แล้วเริ่มใหม่ ณ จุดสุ่ม
- server บันทึกไม่ได้ชั่วคราว และโค้ด server ล้มกับ mutation บางชุด
- เวอร์ชันไม่ตรงกันหลัง deploy
- ตั้งแต่ M3: client ล้มและเริ่มใหม่ ณ ทุกจุดระหว่างออกเลข, เขียน outbox, ส่ง และรู้ผล
- ตั้งแต่ M3: การสลับแท็บตัวทำงานกลางคัน โดยตัวเก่ายังทำงานค้างอยู่ชั่วครู่ และการเขียน outbox จากแท็บที่ไม่ใช่ตัวทำงาน

สิ่งที่ต้องเป็นจริงทุก seed:

- **I1 ลงเอยตรงกัน** เมื่อทุกเครื่องเชื่อมต่อและคิวว่าง view ของทุกเครื่องเท่ากับข้อมูลของ server
- **I2 ไม่หาย ไม่ซ้ำ และไม่หลอก** การกระทำของผู้ใช้ทุกครั้งจบแบบใดแบบหนึ่งพอดี คือถูก server นำไปใช้หนึ่งครั้ง หรืออยู่ในรายการที่ไม่สำเร็จของเครื่อง ชุดที่ server นำไปใช้ต้องเท่ากับชุดที่เครื่องถือว่าถูกรับ
- **I3 เดินหน้าอย่างเดียว** `lastSyncId` ของเครื่องไม่ลดลง และ delta ถูกใช้ตามลำดับโดยไม่ข้าม
- **I4 เห็นของตัวเอง** view ของเครื่องสะท้อน mutation ที่ยังรออยู่ของเครื่องนั้นเสมอ
- **I5 ทั้งชุดหรือไม่เลย** ไม่มี view ใดเห็น mutation เพียงบางส่วน
- **I6 ออกจากคิวถูกจังหวะ** mutation ออกจาก pending ก็ต่อเมื่อถูกปฏิเสธ หรือถูกรับที่ S และ `lastSyncId` ถึง S แล้ว
- **I7 ไม่ค้าง** เมื่อการเชื่อมต่อนิ่งและ server ปกติ mutation ทุกชุดรู้ผลภายในจำนวนขั้นที่กำหนด

เกณฑ์ขั้นต่ำ **[ผู้สร้าง ปรับขึ้นได้ ไม่ปรับลง]**: CI ของทุก PR รันอย่างน้อย 1,000 seed และพิมพ์ตัวนับว่าความผิดปกติแต่ละชนิดเกิดกี่ครั้ง แต่ละชนิดต้องเกิดอย่างน้อย 50 ครั้ง seed ที่ทำให้พังต้องพิมพ์ออกมาและรันซ้ำได้

โค้ดแกนของ server ที่ตัวจำลองทดสอบต้องเป็นชุดเดียวกับที่รันจริง

### การทดสอบอื่น

- ที่เก็บข้อมูลสองแบบของแกน server ผ่านชุดทดสอบเดียวกัน
- WorkspaceDO ในสภาพแวดล้อมของ Workers: ข้อมูลอยู่รอดหลังหลับแล้วตื่น, การตรวจสิทธิ์, การไม่ทำซ้ำ, การปิดการเชื่อมต่อที่เวอร์ชันไม่ตรง, การถอดสมาชิก
- End-to-end ด้วยเบราว์เซอร์สองตัว: คนหนึ่งแก้ อีกคนเห็น, แก้รายละเอียดชนกัน, ฉากไม่มีเน็ตตามเกณฑ์ของ M3, การสลับแท็บ, การใช้งานด้วยคีย์บอร์ด, คีย์ลัดขณะแป้นเป็นภาษาไทย, การตรวจการเข้าถึง
- หน้าเดโมไม่ส่ง request ไปยัง API
- ความเร็วที่ข้อมูล 10,000 issue
- CI รันทุก PR

- จำนวนแถวที่เขียนต่อ mutation
- ข้อความ WebSocket และ ping นับโควตา request อย่างไร
- การกู้คืนย้อนเวลาใช้ได้บนแผนฟรีหรือไม่

ถือว่าเสร็จเมื่อ:

- เปิด PR แล้ว CI ผ่าน และมีลิงก์ที่เปิดได้จริง ทั้งสองคนรันแอปในเครื่องได้

- ซ้อมกู้คืนจากไฟล์ส่งออกสำเร็จหนึ่งครั้ง
- งาน login ผ่านการตรวจด้านความปลอดภัย
- มีเอกสารอธิบาย engine ฉบับสั้นที่เจ้าของตรวจและแก้เองแล้ว

### M2 หน้าจอครบ (งานหน้าเว็บล้วน)

ส่งมอบ: project, label, board, ตัวกรองและค้นหา, command palette และคีย์ลัด, ถังขยะ, ตั้งค่า

ถือว่าเสร็จเมื่อ: ทุกอย่างในขอบเขตรุ่นแรกทำได้โดยไม่ใช้เมาส์ รวมถึงตอนแป้นเป็นภาษาไทย และเทสต์ end-to-end กับการตรวจการเข้าถึงผ่าน

### M3 Offline (งาน engine ล้วน)

ส่งมอบ: ข้อ 8.6 ถึง 8.10 ส่วนที่เป็นของ M3 ทั้งหมด และตัวจำลองที่มีความผิดปกติของ M3

ถือว่าเสร็จเมื่อฉากนี้ผ่านในเทสต์ end-to-end:

1. ปิดเน็ต แล้วเปิดแอปได้
2. สร้างและแก้ issue
3. ปิดแท็บ แล้วเปิดแท็บใหม่ขณะยังไม่มีเน็ต
4. เห็นการแก้ไขทั้งหมดจากข้อ 2
5. ต่อเน็ต แล้วทุกอย่างไปถึง server ครบและไม่ซ้ำ

และ: รายการที่ไม่สำเร็จยังอยู่หลังปิดแล้วเปิด, ตัวจำลองผ่านเกณฑ์ขั้นต่ำ, เอกสารอธิบาย engine อัปเดตส่วน offline แล้ว

### M4 พร้อมใส่ portfolio (ทั้งสองคน)

ส่งมอบ: หน้าเดโมตามข้อ 12, README และบทความอธิบาย engine, วิดีโอสั้น, การตรวจการเข้าถึงและความเร็วที่ 10,000 issue

ถือว่าเสร็จเมื่อ: คนแปลกหน้าที่ได้ลิงก์ลองเดโมได้ภายใน 10 วินาทีโดยไม่สมัครและไม่มี request ไปยัง API และ README อธิบาย engine พร้อมผลทดสอบ

### ลำดับ

M0 → M1 → (M2 กับ M3 ขนานกัน) → M4

ตัวเลือกแรกหลังรุ่นแรก: comment, undo, ช่องทางสำหรับ AI agent, หลายแท็บที่ทำงานสดพร้อมกัน

## 16. ความเสี่ยง

| ความเสี่ยง | การรับมือ |
|---|---|
| บั๊กของ engine ทำให้ข้อมูลเพี้ยนหรือหาย | ตัวจำลองกับ I1 ถึง I7, server เป็นตัวจริง, server ตรวจการใช้เลขซ้ำ, ปุ่มล้างสำเนา, รายการที่ไม่สำเร็จ |
| เพดาน CPU 10 ms ของแผนฟรีแน่นเกินไป | แบ่งงานเป็นหน้า, วัดจริงใน M0 และกำหนดเพดานจากผลวัด, ทางออกคือแผน 5 ดอลลาร์ต่อเดือน |
| โควตารายวันหมด server บันทึกไม่ได้จนถึง 07:00 | เดโมไม่ใช้ server, ผลแบบ "ยังไม่ได้บันทึก" ทำให้การแก้ไขรออยู่ในเครื่องแล้วส่งเองเมื่อโควตากลับมา, ก่อน M3 มีคำเตือนก่อนออกจากหน้า |
| คนนอกยิง request ใส่เส้นทาง login จนโควตาของ Worker หมด สมาชิกเชื่อมต่อใหม่ไม่ได้ชั่วคราว | แอปทำงานต่อแบบ offline ได้ และกันไม่ได้เต็มร้อยบน `workers.dev` ถ้าเกิดจริงให้ใช้โดเมนของตัวเองพร้อมกฎจำกัดอัตรา |
| การย้าย schema ทำข้อมูลจริงเสีย | ส่งออกก่อน deploy, ซ้อมกู้คืน, การกู้คืนย้อนเวลาถ้าใช้ได้ |
| ทั้งสองคนยังไม่คุ้น Cloudflare | ตรวจเอกสารจริงก่อนเขียนทุกส่วนที่แตะ Cloudflare, แกน engine ไม่ผูกกับ Cloudflare |
| ขอบเขตบวม เพราะ Linear มีฟีเจอร์มาก | รายการสิ่งที่ไม่ทำในข้อ 3 และ milestone ในข้อ 15 |
| สองคนแก้ชนกัน | ขอบเขตตามโฟลเดอร์, สัญญากลางที่ตกลงก่อนใน M0, M2 กับ M3 ไม่แตะไฟล์ชุดเดียวกัน |
| service worker ทำให้ผู้ใช้ค้างอยู่ที่แอปรุ่นเก่า | กติกาในข้อ 8.9 และ 8.10 และเทสต์ end-to-end ของการเปลี่ยนเวอร์ชัน |
| M1 เป็นช่วงที่ใหญ่ที่สุดและตกอยู่กับคนเดียว | แผนงานต้องแบ่ง M1 เป็นขั้นย่อยที่ตรวจได้ทีละขั้น |

## 17. สิ่งที่ปล่อยให้ผู้สร้างตัดสิน

- Library ที่ใช้: router, markdown, ลากวาง, ตัวห่อ IndexedDB, ตัวตรวจข้อมูล, ตัวช่วย login, fractional index, service worker
- รูปแบบข้อความจริงระหว่างเครื่องกับ server, โครงตาราง SQLite และ D1, โครง IndexedDB
- รูปร่างของช่องทางที่เก็บข้อมูลของแกน server
- วิธีส่งตัวตนที่ตรวจแล้วจาก Worker ไปยัง WorkspaceDO ภายใต้เงื่อนไขในข้อ 9.1
- bootstrap และ delta ย้อนหลังส่งทาง HTTP หรือ WebSocket
- ขนาดหน้า, เพดานอัตรา และเพดานอื่น ภายใต้เกณฑ์ของ M0
- วิธีวัด CPU
- รูปแบบของ URL ของ issue ภายใต้เงื่อนไขว่าเปิดด้วย id ได้เสมอ
- รายการคีย์ลัดทั้งหมด
- การตั้งค่า CI และขั้นตอน deploy
